# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**easyWp** — a lightweight Fabric mod for Minecraft that adds persistent, per-world waypoints (create/edit/list, hide/focus, share across Overworld↔Nether, optional TP for operators, automatic death waypoints, and manual two-way import/export with Xaero's Minimap). Client-side only; the common/server entrypoint does nothing but log. Mod ID: `easywp`. Licensed CC0 1.0.

This file is the sole source of technical documentation for the project.

## Repository structure

Multi-module Gradle layout declared in `settings.gradle` (`include 'common', 'versions:26.1', 'versions:26.2', 'versions:26.3'`). Three Minecraft versions are supported — there is no legacy single-module copy and no historical-version scaffolding. Nothing below is written against a fixed count: `checkSharedSources` reads the version list off the included subprojects, so a fourth is `settings.gradle` plus a `versions/<x>/` directory, not an edit to the checks.

- `common/src/main/java/com/easywp/EasyWp.java` — the shared/server `ModInitializer` (just logging). There is no client code in `common/` — the entire client layer (`versions/*/src/client/java/com/easywp/client/`) is intentionally duplicated per version rather than shared. This isn't just a style choice: `common/build.gradle` declares only `fabric-loader` and `slf4j-api` as dependencies, no Minecraft artifact at all, and `common` is its own real Gradle subproject with its own `:common:compileJava` task — so any class in `common/src/main/java` that imports `net.minecraft.*` (client-only or not, e.g. `BlockPos`) would fail to compile standalone, even though it would compile fine once merged into a version's own sourceSet (see below). Pinning `common` to one Minecraft version just to satisfy its own compile would be fragile (it wouldn't actually validate compatibility with the *other* version), and dropping the `java` plugin to stop compiling it standalone is a bigger structural change than the duplication it would save. **Twenty-two of the twenty-seven client files are byte-identical across all three versions** (`Waypoint`, `ModConfig`, `I18nHelper`, `ModernButton`, `WaypointDisplayMode`, `WaypointSortMode`, `WaypointPing`, `ModMenuIntegration`, `UiPalette`, `Icons`, `ShaderDetector`, `DeathWaypointManager`, `ModConfigScreen`, `ModKeyBindings`, `WaypointListScreen`, `DimensionNames`, `XaeroBridge`, `XaeroMinimapBridge`, `XaeroSync`, `XaeroLinkLedger`, `WaypointColors`, `ImportWorldScreen`) — keep them in sync by editing one, diffing, and copying to the *others*, not by trying to relocate them. `.gitattributes` pins the whole tree to LF precisely so that `diff` stays meaningful here.

  The root `checkSharedSources` task enforces this on every `build`, in **both** directions, and across **all** the trees rather than a single pair:
  - a listed file that is not byte-identical in every version fails the build, so a divergence cannot ship. The message names which copies agree with which (`26.1+26.2 vs 26.3`), because with three trees "they differ" no longer says where the edit went missing;
  - a file that is byte-identical in *every* version but *not* listed also fails, with instructions to add it. That second half exists because being identical-but-unlisted is precisely the state in which a later drift goes unnoticed — `ModMenuIntegration.java` sat that way for a while. `intentionallyUnsharedSources` is the escape hatch for a file that matches everywhere only by coincidence; it is empty today.

  Note the asymmetry three trees introduce: a file identical in *some* versions is neither guarded nor flagged. `EasyWpClient.java` is the same in 26.2 and 26.3 and different in 26.1, which is the intended state, so it stays off both lists — it does not belong in `intentionallyUnsharedSources`, which is only for a file that matches in all of them.

  Only five files differ, and only two of them meaningfully:
  - `ClientCompat.java` — the shim that *exists* to hold the difference (see Entry points below). All three copies differ from each other.
  - `EasyWpClient.java` — one line, `LevelRenderEvents.END_MAIN` on 26.1 vs `COLLECT_SUBMITS` on 26.2 and 26.3, whose copies are identical.
  - `WaypointCreateScreen.java` — identical code, one differing javadoc paragraph about how each version projects the label; 26.3 carries 26.2's, since it projects the label the same way.
  - `WaypointRenderer.java` and `WaypointRenderTypes.java` — genuinely different code (see Rendering below). 26.2 and 26.3 are close but not identical: 26.3's renderer differs from 26.2's by one renamed call, and its render types by the whole pipeline-construction story below.

  Before `ClientCompat` existed, four more files carried 26.2's renamed vanilla calls inline (`Minecraft.setScreen` → `setScreenAndShow`, `Minecraft.gui.setOverlayMessage` → `gui.hud.setOverlayMessage`), which kept them off the guarded list for no better reason than two method names. Route any future rename of that shape through the shim rather than inline, or the file drops out of the shared set and stops being checked. The 26.3 port is what that rule was written for: it renamed a key-constant source, an enum constant and a *type's package*, across four otherwise-shared files, and all of it went through the shim — see Entry points below for what had to change and why a moved type needs a method that hides it rather than one that takes it.
- `common/src/main/java/com/easywp/JsonStore.java` is the exception that proves the rule above: it imports nothing but `java.nio`, so it compiles standalone against this module's Minecraft-free dependency set and every version picks it up from the shared source directory. It is where the durable read/write for both JSON stores lives (see Persistence below). Anything else that is genuinely Minecraft-free belongs here too.
- `common/src/main/resources/` **does** hold real shared content — non-code resources aren't compiled, so none of the above applies. Every version already merges it in via `resources.srcDirs += project(":common").file("src/main/resources")`. Everything byte-identical between versions lives there: the eight lang JSON files, the mod icon, `textures/waypoint_marker.png`, the 14 icons under `textures/gui/`, and `easywp.mixins.json`. `fabric.mod.json` stays per-version — its `depends` block legitimately differs. So does one texture: `label_backdrop.png`, a 1x1 opaque white pixel that exists only because 26.2's and 26.3's backdrop render types need a bound sampler where 26.1's colour-only pipeline does not, so it is duplicated under `versions/26.2/` and `versions/26.3/` and absent from 26.1. It is the single per-version asset; everything else under `assets/` is shared.
- `versions/26.1/` — stable branch, Minecraft `26.1.2`, Fabric API `0.155.2+26.1.2`, uses the "billboard 3D" renderer (see below).
- `versions/26.2/` — Minecraft `26.2`, Fabric API `0.156.0+26.2`, uses the newer `SubmitNodeCollector` render pipeline: same 3D billboard architecture as 26.1, but geometry is submitted through `LevelRenderEvents.COLLECT_SUBMITS` instead of drawn directly in `END_MAIN`. Do not port 26.1's `WaypointRenderer.java` here verbatim — the render APIs diverged; the Rendering section below is the record of how, and each file's own javadoc carries the rest.
- `versions/26.3/` — Minecraft `26.3`, Fabric API `0.160.5+26.3`, Mod Menu `21.0.0-beta.1` (the only Mod Menu built for 26.3 so far; it is `clientCompileOnly` and never bundled, so a beta costs nothing), Xaero's Minimap `26.5.1` + xaerolib `1.7.8` (26.5.0, which 26.1/26.2 pin, was never published for 26.3). Same submit-phase architecture as 26.2, and deliberately so — Fabric's `LevelRenderEvents.COLLECT_SUBMITS`, `LevelRenderContext` and `SubmitNodeCollector.submitCustomGeometry`/`submitText` all kept their 26.2 signatures. What did change is everything *underneath* the render types: 26.3 replaced the blaze3d pipeline layer with `com.mojang.renderpearl` (which also brought a Vulkan backend), made `RenderPipelines.register` and every pipeline snippet private, deleted `OutputTarget`, and replaced the multi-target transparency compositor with order-independent transparency. It also replaced GLFW with SDL, which is why `ClientCompat` grew key constants. See Rendering below.
- Each version subproject compiles `common/` directly into its own jar (`java.srcDirs += project(":common")...` plus `implementation project(":common")`) — `common` is not published as a separate artifact. All three `versions/*/build.gradle` files are byte-identical; everything that varies between them lives in their own `gradle.properties`. Nothing checks that, the same as before — a new version's `build.gradle` is a `cp` of an existing one, and a difference that creeps in there will not fail a build.
- `common/build.gradle` compiles at **Java 21** while both version subprojects compile at **25**. That is not an oversight: `common` only ever has to satisfy its own standalone `:common:compileJava`, and the sources that actually ship are recompiled at 25 inside each version's `main` sourceSet, which is what `fabric.mod.json`'s `"java": ">=25"` and the mixin config's `JAVA_25` refer to. Keep new `common/` code inside the Java 21 language level or the standalone compile breaks even though the shipped jar would have been fine.

A prior attempt to also support older Minecraft versions (`1.21.1`, `1.21.3`, `1.21.8`, `1.21.11`) was abandoned and removed; see git history if that work is ever resumed.

## Build & run

Requires JDK 25. Gradle Wrapper (Gradle 9.5.1) and Fabric Loom `1.17-SNAPSHOT` are pinned in `gradle/wrapper/` and `gradle.properties`.

```bash
./gradlew build
```

Builds every included subproject and produces:
- `versions/26.1/build/libs/easywp-<mod_version>+26.1.x.jar`
- `versions/26.2/build/libs/easywp-<mod_version>+26.2.jar`
- `versions/26.3/build/libs/easywp-<mod_version>+26.3.jar`

Other useful tasks:

```bash
./gradlew :versions:26.1:build      # build a single version
./gradlew :versions:26.1:runClient  # launch a dev client for that version (working dir: run/)
./gradlew :versions:26.2:runClient
./gradlew :versions:26.3:build
./gradlew :versions:26.3:runClient
./gradlew clean
```

The mod version is global and set once in root `gradle.properties` (the `mod_version` property); each version subproject appends its own `minecraft_version_suffix` from its own `gradle.properties` to form the jar name. There is no lint task. Correctness is verified via `build`, which compiles every version and runs three checks — `checkSharedSources` (see Repository structure), `checkLangParity`, and `:common:test` — plus manual in-game testing through `runClient` for everything those cannot reach, which is most of the mod. Each can also be run on its own:

```bash
./gradlew checkSharedSources   # every copy of every shared client source still agrees
./gradlew checkLangParity      # every lang file carries en_us.json's exact key set
./gradlew :common:test         # JsonStore + XaeroWaypointFormat unit tests
```

`checkLangParity` fails if any lang file is missing a key that `en_us.json` has, if it carries a key `en_us.json` does not (which is a typo'd key nothing will ever look up — the string stays untranslated while the file looks complete), or if one of the six `es_*` copies has drifted from `es_es.json`. The Spanish copies are listed in `spanishCopiesOfEsEs` in the root `build.gradle`; drop a locale from that list the day it earns genuinely regional wording.

### Tests

`common/` is the only module where a test suite can exist at all: every other class needs a running client, while anything living in `common/` (by construction) touches nothing but `java.nio`/plain text. Two suites live there today:

- `JsonStoreTest` — `JsonStore` is where a bug costs the most, since the per-world waypoint file is the only copy those waypoints exist in, so the suite pins the guarantees rather than leaving them to be re-derived from the implementation: round-tripping, parent-directory creation, no `.tmp` left behind, no `.bak` on the first write, the `.bak` holding the *replaced* revision on later ones, UTF-8 for non-ASCII waypoint names, a shorter document fully replacing a longer one, and recovery from a truncated target. Checked against two deliberate mutations (skipping the backup snapshot; writing straight to the target instead of via the temp file) and caught both.
- `XaeroWaypointFormatTest` — round-tripping every field, unknown trailing fields preserved instead of dropped, malformed/too-short lines skipped rather than guessed, non-waypoint lines preserved through both `merge` and `removeAll`, `merge`'s add-only idempotency and its guarantee that nothing the caller didn't mention is ever removed, `removeAll` dropping only the waypoints named (a same-named waypoint at another position survives) and matching on name + X + Z *ignoring Y* so the file path agrees with the live bridge, exported waypoints landing in Xaero's own default set, the 21-entry color palette's round-trip, `:` in a name sanitized rather than desyncing the line, non-ASCII names, and the exact `xaero-waypoint:` chat line Xaero's own receiving parser accepts. Checked against deliberate mutations (`merge` not deduplicating; `merge` dropping what was already in the file; `removeAll` matching on Y as well; `removeAll` dropping non-waypoint lines; the chat line carrying the destination field it must omit) and caught all of them.

JUnit 5 is pinned by `junit_version` in the root `gradle.properties`. Anything added to either suite should be held to the same bar: checked against a real, deliberate break in the implementation, not just passing against the current one.

### CI

`.github/workflows/build.yml` runs `./gradlew build` on every push and pull request (Ubuntu, Microsoft JDK 25) and uploads the resulting jars. There is no separate test job: `build` already runs `:common:test`, `checkSharedSources` and `checkLangParity`, so the one command is the whole gate. The artifact path is `versions/*/build/libs/*.jar`, not `build/libs/`: the root project has no `java` plugin at all, so nothing is ever produced there, and the workflow used to upload an empty artifact because of it.

`runClient` writes its sandbox to the invoking subproject's own `run/` — `versions/26.2/run/config/easywp/` holds a real `config.json` and a `waypoints_sp_New_World.json`, useful as live examples of both file formats. The `run/` at the repository root is a leftover from the abandoned single-module layout. All of it is gitignored (`run/`, and now `logs/` as well, after an empty `versions/26.2/logs/latest.log` was committed once by accident); none of it is mod source.

## Architecture

### Entry points (`fabric.mod.json`, per version)

- `com.easywp.EasyWp` (in `common/`) — `ModInitializer`, server/common side, effectively a no-op (just logs startup).
- `com.easywp.client.EasyWpClient` (per-version) — `ClientModInitializer`, and the whole of the client wiring: `ModKeyBindings.register()`, `WaypointRenderTypes.init()` (which must run before the first frame — see Rendering), the render hook (`LevelRenderEvents.END_MAIN` on 26.1, `COLLECT_SUBMITS` on 26.2 and 26.3), and `ClientTickEvents.END_CLIENT_TICK` for `DeathWaypointManager`. `WaypointRenderer` itself has no init step: its state is all static field initializers with no side effects, so it is simply first-touched by whichever of those hooks fires first.
- `com.easywp.client.ClientCompat` (per-version, not an entrypoint) — the shim holding every vanilla name that changed between versions without its meaning changing. It is the one client file that is *supposed* to differ in every tree, and it exists so the screens and managers that would otherwise carry those renames inline can stay byte-identical and therefore guarded by `checkSharedSources`. Add to it only for renames of this shape — same semantics, different vanilla name. Where the versions genuinely do different work (the render hook, the three renderers) the difference belongs in the caller, where it can be explained. It now holds:
  - `setScreen` and `setOverlayMessage` — the 26.1→26.2 renames (`setScreen`/`setScreenAndShow`, `gui.setOverlayMessage`/`gui.hud.setOverlayMessage`), unchanged again in 26.3.
  - `KEYBOARD` and the seven `KEY_*` ints — 26.3 replaced GLFW with SDL. `org.lwjgl.glfw.GLFW` is simply not on the 26.3 classpath, its key codes moved onto `InputConstants` itself (`InputConstants.KEY_K`, and SDL's own `KEY_RETURN`/`KEY_NUMPADENTER` for the two Enters), and `InputConstants.Type.KEYSYM` — GLFW's name for a layout-mapped key — became `Type.KEYBOARD`. `ModKeyBindings` and `WaypointCreateScreen` name the constants here instead, and stay shared.
  - `blitTinted` — the one that is *not* shaped like the others, and the reason worth reading. 26.3 moved `RenderPipeline` from `com.mojang.blaze3d.pipeline` to `com.mojang.renderpearl.api.pipeline`. A moved **type** cannot hide behind a method that takes it as a parameter, which is what `Icons.drawMarkerIcon(g, pipeline, ...)` and the two screens' `RenderPipeline pipeline = RenderPipelines.GUI_TEXTURED;` were doing — four shared files naming the type in their own signatures. So the shim takes the *texture* and looks the pipeline up itself. Every call site passed `GUI_TEXTURED` anyway, so nothing was lost by not letting them choose, and `Icons`, `WaypointListScreen` and `WaypointCreateScreen` stopped naming the type at all. The general rule: when a rename moves a type rather than a method, the shim has to swallow the type, not accept it.
- `com.easywp.client.ModMenuIntegration` (per-version) — optional `modmenu` entrypoint returning `ModConfigScreen`. Fabric only instantiates it when Mod Menu is installed, and Mod Menu is a `clientCompileOnly` dependency (`18.0.0` for 26.1, `20.0.1` for 26.2, `21.0.0-beta.1` for 26.3, from the Terraformers maven), so it is never bundled. Note that Loom 1.17 exposes no `mod*` configurations at all — this project declares even Fabric API through plain `implementation`, and remapping happens anyway.
- `com.easywp.client.XaeroBridge` (shared, not an entrypoint) — the second optional `clientCompileOnly` dependency, same shape as Mod Menu but gated explicitly rather than by Fabric's own conditional-instantiation trick: `xaero.minimap:xaerominimap-fabric-<minecraft_version>:26.5.0` (pinned per version in `gradle.properties`, plus `xaero.lib:xaerolib-fabric-<minecraft_version>:1.7.3` pinned explicitly rather than left to the POM's `[1.7.0, 1.8)` range), from `https://chocolateminecraft.com/maven`, added to both `versions/*/build.gradle` by hand — those two files are byte-identical and nothing checks that, the same as every other line in them. See Xaero's Minimap integration below for why the gate is two separate questions (`isModInstalled()` vs. `isAvailable()`) plus a `LinkageError` catch rather than Mod Menu's simpler pattern, and why `XaeroMinimapBridge` is the one other file (besides `ClientCompat`) allowed to import from outside `net.minecraft.*`/this mod's own packages.

`environment` is `client`: the common entrypoint only logs, and nothing in the mod needs to run server-side.

### Keybindings & input

`ModKeyBindings` registers five keys under one custom `KeyMapping.Category` (`easywp:easywp_controls`, named by the `key.category.easywp.easywp_controls` lang key) and then drives all of them from a single `ClientTickEvents.END_CLIENT_TICK` handler using `while (key.consumeClick())`:

| Key | Default | Action |
| --- | --- | --- |
| `key.easywp.toggle` | `K` | Cycles `WaypointDisplayMode` (world markers ⇄ disabled) and shows the new state as an overlay message |
| `key.easywp.create` | `N` | Opens `WaypointCreateScreen` pre-filled with the player's own block position |
| `key.easywp.list` | `J` | Opens `WaypointListScreen` |
| `key.easywp.ping` | `H` | Opens `WaypointCreateScreen` pre-filled with `WaypointPing.target(client)`, the crosshair raycast. Was `V` until Fast Ping (below) took it over. |
| `key.easywp.fast_ping` | `V` | Creates a waypoint at the crosshair raycast directly, with no screen - the form's own default-name and restore-visibility logic duplicated inline since there is no `WaypointCreateScreen` instance to call into. Replaces what used to be a no-menu *quick-create* bound to `G` and targeting the player's own feet; Fast Ping keeps the no-menu part but targets the same ray as classic Ping above, sharing its `ModConfig.Ping` settings (range, fluids, follow-render-distance) rather than growing a second copy of them. Named `easywp.create.ping_name` ("Ping #N"), colored with `WaypointColors.random()`, and flagged `Waypoint.fastPing` so `ModKeyBindings.countFastPings()` can number the next one without string-matching the name. Not `B`: that's Xaero's Minimap's own default "new waypoint" key, and the two would otherwise fire on the same press. |

Rebinding happens in Minecraft's own Controls screen — `ModConfigScreen` deliberately does not duplicate it. One non-obvious detail lives in that same tick handler: the "remember visibility across restarts" setting is applied on the **first tick**, not in `onInitializeClient()`, because `ModConfig.get()` needs `Minecraft.getInstance().gameDirectory`, which is not guaranteed ready during client init. A one-shot `appliedRememberedVisibility` flag guards it.

### Data model

`Waypoint` is a POJO: `name`, `pos` (`BlockPos`), `color` (ARGB int), `dimension`, `shared` (mirrored between Overworld/Nether at a 1:8 ratio), `visible`, `focused`, `forceVisible`, `death` (marks an automatic death waypoint), `fastPing` (marks one Fast Ping created, see Keybindings above), `createdAtMillis`. It also carries a small render-side label cache (`cachedLabelText`/`cachedLabelWidth` plus the inputs they were built from, checked via `labelCacheMatches()`/written via `setCachedLabel()`) — riding on the waypoint itself rather than a separate map, since nothing else in the mod uses a store abstraction either, and it needs no cleanup when a waypoint is deleted (see Rendering below). The live list for the current world is held in-memory as a static `List<Waypoint>` on `WaypointRenderer`, read/written directly by the UI screens and the renderer — there is no separate state/store abstraction. `forceVisible` and `fastPing` are setter-only (not in the canonical constructor) for the same reason: each has exactly one creation path that constructs a plain `Waypoint` and flags it after, so adding either to the constructor would mean touching call sites that never need it. `WaypointCreateScreen.saveWaypoint()` clears `fastPing` the moment a Fast Ping is edited, the same way it already clears `death` - once reshaped by hand it's a permanent waypoint the player meant to keep, not a throwaway ping, and it stops counting toward the next one's `Ping #N` number. Two more flags have come and gone, and a `waypoints_*.json` written while either existed still carries them — which Gson simply ignores, so there is nothing to migrate: `portal` marked a waypoint the automatic portal-crossing feature created (removed along with that feature), and `fromXaero` marked one an automatic Xaero import had created so deleting it locally also deleted it from Xaero (removed along with the automatic sync — see Xaero's Minimap integration below for what replaced it).

### Persistence

Three separate JSON stores, all under `<game_dir>/config/easywp/`:
- **Per world/server**: `waypoints_<worldId>.json` (`worldId` = `sp_<sanitized_world_name>`, `mp_realm_<sanitized_realm_name>`, `mp_<sanitized_ip>`, or `mp_lan`).

  **A Realm is filed under its name, a direct server under its address, and that distinction is load-bearing.** `ServerData.ip` is the only address the client has, and for a direct server it is a stable identity. For a Realm it is not: it is the session address Mojang's backend resolves per join attempt (`RealmsJoinInformation.address()`, region-routed via `RegionData`), which `RealmsServer.toServerData(String)` drops straight into that same `ip` field — confirmed from the client jar's own bytecode. It changes on its own, with nothing the player did: a Realm that was updated between two sessions came back on a different address, which produced a different `worldId`, which loaded an empty file, and the waypoints looked deleted while the real file sat intact under the previous address. `ServerData.Type.REALM` is what separates the two cases, read via `ServerData.isRealm()` (vanilla's own one-line `type == Type.REALM`, so no extra import and no assumption about the accessor's name). That the branch fires at all is confirmed the same way: `RealmsConnect$1` builds `server.toServerData(host + ":" + port)` and hands it to `ClientHandshakePacketListenerImpl`, which is what becomes `Minecraft.getCurrentServer()`.

  **The name is the best identity reachable from here, not a perfect one, and the difference is worth stating.** `RealmsServer` carries a genuinely stable `long id`, but `toServerData` does not pass it on and `ServerData` is all `getWorldId()` ever sees, so the name is what is left. It only changes when the owner renames the Realm — rare, deliberate, and fixable by renaming the file to match, which a per-join address is not. It notably does **not** change when the Realm switches to a minigame: that is `RealmsServer.minigameName`, a separate field, and `RealmsConnect` sets it on the packet listener rather than on this `ServerData`.

  `RealmsServer.parse` builds `name` fresh from the Realms API's JSON on every fetch (confirmed from bytecode: a straight `GuardedSerializer.fromJson` with no cache layer in front of it), so short of an actual rename this value is exactly as stable as it looks — there is no staleness path where the same Realm hands back a different name across two sessions.

  Three limits come with that, one handled and two accepted — all three are the same root cause (two different Realms landing on the same *file* name), not three unrelated bugs, and all three needed something more specific than "same name" to see:
  - **`ServerData.name` is never null on a Realm, so a null-check is the wrong guard.** `toServerData` is `new ServerData(Objects.requireNonNullElse(this.name, "unknown server"), address, REALM)` — vanilla has already substituted a *constant* literal. Letting it through would file every unnamed Realm into one shared `waypoints_mp_realm_unknown_server.json`, showing each other's waypoints. `realmFileName()` rejects that literal (and a blank name) and falls back to the address instead: mixing two Realms' lists together is worse than the instability this branch exists to fix, which only makes waypoints look missing while the real file stays intact and recoverable. This one is handled.
  - **Two Realms with the identical raw name collide**, and nothing in `ServerData` can disambiguate them — `RealmsServer` carries a real `long id`, but it never reaches `ServerData`. Accepted: the fix is renaming one of them, and this is a real regression against the old address scheme, which never collided this way (it collided a different way instead, by changing under a single Realm — see above).
  - **Two Realms with *different* raw names can still collide, because sanitizing or filesystem case-folding can make them equal.** `UNSAFE_FILENAME_CHARS` maps `"My Realm"` and `"My:Realm"` to the same `My_Realm`; independently, Windows and default macOS resolve file names case-insensitively, so `"MyRealm"` and `"myrealm"` address one file on this project's own dev machine even though the sanitized strings differ. Neither collision needs a rename, and neither is exotic enough to dismiss. Accepted for the same reason as the identical-name case — nothing past the name is available to disambiguate with, and the fix is the same: rename one Realm.

  `getWorldId()` lives in `WaypointRenderer`, which is **not** a shared source, so this branch exists as three hand-maintained copies. Nothing checks them against each other; the three files are identical in this method today and an edit to one has to be repeated in the other two by hand.

  Orphaned files from before that fix are left alone on purpose. A player who used a Realm under an older build has their waypoints in a `waypoints_mp_<old-address>.json` nothing will open again, and *which* file that is cannot be decided from here: a session address is opaque and carries nothing tying it back to a Realm, so an automatic rename could just as easily adopt some unrelated server's list. `loadFromFile` instead logs one INFO line the first time a Realm comes up empty, naming the `waypoints_mp_*.json` files present and the name to rename one to. That is the whole migration: a pointer, never a move.

  **The manual cross-world import (`ImportWorldScreen`, reached from a new "Import" section in `ModConfigScreen`) is what a player does with that pointer**, and it exists for exactly this case - a Realm's own file address-hopping and stranding waypoints under an old name - though nothing about it is Realm-specific: it lists every `waypoints_*.json` under the config directory except the current world's own (`WaypointRenderer.listOtherWorldFiles()`), one full-width row per file naming the world/server (`prettyWorldName()`, the lossy inverse of `getWorldId()`'s four prefixes - `sp_`/`mp_realm_`/`mp_`/`mp_lan` - good enough for display, never used for anything else) and how many waypoints it holds (`countWaypointsIn()`). Clicking a row imports immediately; the screen stays open afterward so a second file can be imported in the same visit.

  **Importing is additive and deduplicated, and it is the only mode the screen offers.** `WaypointRenderer.mergeFrom()` adds only the incoming waypoints not already present under the same identity - name, exact position, and dimension - and never replaces or removes anything from the current world's list, because a `waypoints_*.json` may be the only copy of some player's waypoints and a destructive import is not a risk worth offering a button for. This identity check is deliberately *not* the name+X+Z (no Y) rule `XaeroSync`/`XaeroWaypointFormat` use for their own dedup: that rule exists only to work around an Xaero waypoint saved without a Y coordinate reporting a synthetic `y = 64`, which is irrelevant here - both sides of this merge are this mod's own JSON, where Y is always real, so throwing that precision away would just make two waypoints at different heights on the same column look identical. `death` and `fastPing` are always cleared on the copy that gets added, the same way `WaypointCreateScreen.saveWaypoint()` already clears them the moment either kind of waypoint is edited by hand (see Data model above): a death waypoint's dwell-timer deletion and a Fast Ping's numbering both belong to the world that created them, and carrying either into a new world would either delete the import for no reason or miscount the next Ping without a matching death/ping ever happening there.

  **`ModConfigScreen`'s new row is `addSmall`, not the `addBig` a single full-width button would suggest, because `addBig(AbstractWidget)` does not exist on 26.1.** `OptionsList.addBig` only takes an `OptionInstance<?>` there; the single-widget overload was added later. `addSmall(AbstractWidget, AbstractWidget)` exists on all three, so the row keeps the screen's usual two-column shape - the import button sized to `CONTROL_WIDTH` like every other control, paired with an invisible, inactive placeholder button standing in where a Reset button would go, since there is nothing on this row to reset.

  Loaded lazily — `WaypointRenderer.checkAndLoadWorldWaypoints()` runs every render frame, but the actual `getWorldId()` computation inside it is gated on `client.level` having changed identity since the last check (true on join/dimension-change, never on an ordinary frame), so the file is only re-read when `worldId` changes. None of this is synchronized, deliberately: every caller — `render()`, `DeathWaypointManager.tick()`, and the screens — runs on the client thread, and so does every mutation of the waypoint list. A `synchronized` block used to wrap just the reload while the rest of the list was mutated freely without it, which bought nothing and implied a thread-safety guarantee the class never had; it was removed rather than extended. Saved with Gson pretty-printing immediately after any mutating action (create/edit/delete/visibility/focus/share) — no periodic autosave, no dirty-cache batching. `visible`/`focused` are optional/nullable in the JSON for backward compatibility with older save files.
- **Global mod settings**: `config.json`, independent of any world, managed by `ModConfig` (marker size/opacity, label uppercase/distance, death-waypoint enable + `maxCount` + arrival radius + grace seconds, delete confirmation, visibility persistence, ping raycast range/fluids/follow-render-distance (shared by classic Ping and Fast Ping - one `ModConfig.Ping` group, one "Ping/FastPing" section header in `ModConfigScreen`, not two), waypoint-list sort mode, Xaero integration enable + chat-format). Grouped by feature into nested classes so new settings groups don't reshape the file; each group is null-checked on load for backward compatibility with older `config.json` files. A group *added later* (like the two above) gets its defaults from its own field initializers via that null-check; a field added to an *existing* group instead gets Gson's zero value for a JSON that predates it — which is why a new setting whose sane default isn't `false`/`0` belongs in a new group, never bolted onto an old one.

- **Per world/server, Xaero link ledger**: `xaero_links_<worldId>.json`, managed by `XaeroLinkLedger` — one `dimension|x|z|name` identity per entry for every waypoint easyWp and Xaero have actually exchanged, which is what lets the two sync buttons propagate deletions without touching waypoints only one side ever had. Written only by those two buttons (see Xaero's Minimap integration below), read fresh on each press rather than cached, and safe to delete: an absent ledger just makes both buttons additive again.

All three stores go through `JsonStore` (in `common/`) rather than writing straight to their destination: the document is serialized in full, written to a sibling `.tmp`, forced to disk, and then moved onto the target atomically, so a crash mid-save can no longer truncate a file that is the only copy those waypoints exist in. Every successful write first snapshots the previous revision to `<file>.bak`, and every load falls back to that snapshot when the main file is missing, empty, or unparseable. `ModConfig` deviates in one place on purpose: if neither the config nor its backup can be read it runs on in-memory defaults **without** saving, because writing would push the unreadable file into the backup slot and destroy the last good revision. `common/src/main/java/com/easywp/XaeroWaypointFormat.java` is the other class (besides `JsonStore`) living in `common/` for the same reason: it is pure text handling (Xaero's `waypoints.txt` line format, read from that mod's own bytecode rather than guessed — see Xaero's Minimap integration below), nothing `net.minecraft.*`, so it compiles standalone and every version shares it unmodified. `common/src/test/` now holds two suites, `JsonStoreTest` and `XaeroWaypointFormatTest`, both run by `:common:test`.

### Rendering — two genuinely different architectures per Minecraft version

This is the trickiest part of the codebase, and the reason the render types carry as much explanatory comment as they do: naive "see-through" 3D rendering gets intercepted by Iris/Oculus shaderpacks' shadow-map pass and turns markers/text pure black when occluded by a block. The reasoning behind each pipeline choice - and the failure it exists to avoid - lives in the javadoc of `WaypointRenderTypes` in each version; read those before changing anything there, since most of the obvious-looking alternatives have already been tried and rejected.

- **26.1 — "3D billboard" approach.** `WaypointRenderer.render()` hooks `LevelRenderEvents.END_MAIN`. Per waypoint: filter by dimension (recomputing position for `shared` waypoints), cull it if it's more than `CULL_MIN_DISTANCE` (8 blocks) away and its direction from the camera is more than `CULL_DOT_THRESHOLD` (dot < -0.5, ≈120°) off the camera's forward vector — a deliberately generous margin over any vanilla/dynamic FOV, computed once per frame from `cameraState.orientation` and reused for every waypoint, so a false cull (visible bug) stays far less likely than skipping the perf win on a borderline case — scale marker size by angular distance, clamp render distance to avoid float precision artifacts, sort back-to-front, then draw a single marker pass through whichever `RenderType` `WaypointRenderTypes.marker(isShaderActive)` returns for the current environment (see below) — overlapping passes were tried and rejected because they wash the marker color out. The label backdrop is hand-drawn geometry (`drawBackdrop`) rather than Font's built-in background box, for the same depth-write reason described below. The label text itself is cached on the `Waypoint` (see Data model above) and only rebuilt/re-measured when the name, uppercase setting, distance toggle, or displayed distance-in-meters actually changed, instead of concatenating and calling `font.width()` every frame regardless. Text glyphs are billboarded toward the camera via `Axis.YP`/`Axis.XP`.
- **26.2 — same 3D billboard approach, different submission path.** Minecraft 26.2's render pipeline rewrite (`SubmitNodeCollector`) means geometry is *queued* rather than drawn immediately, so the hook is `LevelRenderEvents.COLLECT_SUBMITS` instead of `END_MAIN`. The per-waypoint math (dimension filter, camera-angle cull, angular scaling, distance clamp, back-to-front sort, label caching) is the same as 26.1's. Differences: the label gets its own billboard transform, projected to a separate, much nearer fixed distance than the marker (`LABEL_PROJECTION_DIST`, derived from half the player's collision width — the closest a solid block can ever get to the eye standing flush against a wall, with a small margin below that), and marker/backdrop geometry is handed over as `submitCustomGeometry`/`submitText` callbacks rather than written straight into a `VertexConsumer`. The nearer projection exists only because of the depth-testing tradeoff described below: pulling the billboard closer than any reachable wall guarantees it wins the depth test unconditionally, at the cost of shrinking the glyph quads (a perspective projection cancels the shrink back out on screen, but Iris still derives per-pixel lighting from the quad's own deltas — pull the distance in too far and the letters come out grey instead of white, as documented in the constant's own comment).
- **26.3 — same architecture and the same submission path as 26.2, rebuilt on a new pipeline API.** Nothing about *what* is drawn changed: `LevelRenderEvents.COLLECT_SUBMITS`, `LevelRenderContext`, `SubmitNodeCollector.submitCustomGeometry`/`submitText` and the order keys all kept their 26.2 signatures, and `WaypointRenderer.java` is 26.2's file with exactly one rename — `PoseStack.mulPose(Quaternionf)` became `rotateDegrees(Axis, float)` (the `Quaternionf` overload is gone; `rotate(Quaternionfc)` is its literal equivalent, but the degrees-and-axis form says the same thing in one call). That rename stayed inline rather than going through `ClientCompat`, because `WaypointRenderer` is already a per-version file three ways over and the shim exists to keep *shared* files shared. All the per-waypoint math — dimension filter, camera-angle cull, angular scaling, distance clamp, back-to-front sort, label caching, the two projection distances — is unchanged, including `LABEL_PROJECTION_DIST` and its grey-letters caveat.

  `WaypointRenderTypes.java` is where 26.3 really differs, and all of it is *how the same pipeline is constructed*, not what it does:
  - **The pipeline API moved to `com.mojang.renderpearl`.** `RenderPipeline`, `DepthStencilState`, `CompareOp`, `ColorTargetState` and `BlendFunction` left `com.mojang.blaze3d.pipeline`/`.platform` for `com.mojang.renderpearl.api.pipeline` — 26.3's backend abstraction, which is also what brought a Vulkan backend alongside OpenGL. Same records, same constructors, different imports.
  - **There is nothing to register, and nothing to build a private copy *from*.** `RenderPipelines.register` is private in 26.3, and so is every pipeline snippet except the three `OIT_*` ones — so 26.2's `RenderPipelines.register(RenderPipeline.builder(TEXT_SNIPPET)…)` has no counterpart. It needs none either: `PipelineCache.get` compiles a pipeline on its first cache miss (confirmed from its bytecode), which makes `requiredPipelines()`/`optionalPipelines()` a precompile list rather than a registry. In place of the snippet, `WaypointRenderTypes.derive(...)` reads every property off a *built* vanilla pipeline (`getShaders`, `getShaderDefines`, `getBindGroupLayouts`, `getColorTargetStates`, `getVertexFormatBindings`, `getPolygonMode`, `isCull`, `getPrimitiveTopology`, `pushConstantSize`) onto a fresh builder and overrides only the location, the depth state and — for the beacon copy — the first colour target. That is a *closer* copy than a snippet was: it cannot drift from vanilla's own builder chain, because it never transcribes it. The marker copies `RenderPipelines.TEXT_SEE_THROUGH` and the shader-mode marker copies `RenderPipelines.BEACON_BEAM_TRANSLUCENT`.
  - **One property cannot be copied back, and it is logged rather than dropped silently.** `ShaderDefines` stores valued defines as strings while the builder only accepts `int` and `float`, so `derive` parses and warns if a define is neither. None of the two pipelines it copies has a valued define today (vanilla's see-through text carries the single flag `IS_SEE_THROUGH`, read from `RenderPipelines`' bytecode), so the warning has never fired — it exists so that the day it does, it is a log line and not a silently miscompiled shader. If `derive` fails outright it returns `null` and the render types fall back to plain `RenderTypes.textSeeThrough`/`beaconBeam`, which loses the depth write but still draws the marker.
  - **`OutputTarget` is gone entirely** — see the depth-state discussion below, which is where that belongs.
- **Shader immunity comes from `WaypointRenderTypes`, not from render location.** Without a shaderpack the marker and backdrop ride a **private `RenderPipeline`** built on the same shaders as vanilla's `textSeeThrough`/`textBackgroundSeeThrough` (so Iris's shader swap and Minecraft's depth test still treat it identically to vanilla when no pack is loaded), just with the depth state overridden — see below. With a shaderpack loaded, the marker draws through a separate private `RenderPipeline` built on `RenderPipelines.BEACON_BEAM_SNIPPET` (26.1/26.2) or derived from `RenderPipelines.BEACON_BEAM_TRANSLUCENT` (26.3, where the snippet is private), registered with Iris **via reflection** (`IrisApi.assignPipeline(pipeline, IrisProgram.BEACON_BEAM)`) in `WaypointRenderTypes.init()`. Beacon beams are the one piece of world geometry shaderpacks keep emissive and fog-free. `init()` must run before the first frame — Iris resolves the vertex format at assignment time. If the reflection fails for any reason it silently falls back to the vanilla beacon beam render type. **The label backdrop needs the same care and gets it differently**: a private pipeline Iris was never handed is not dimmed, it is skipped entirely, so a shader-active backdrop riding one simply vanishes and leaves the glyphs unreadable against fog or sky. Rather than claim a second Iris program, every version follows the rule that the backdrop rides whatever pipeline the glyphs ride while a pack is loaded - `RenderTypes.textBackgroundSeeThrough()` in 26.1, `RenderTypes.textPolygonOffset(...)` in 26.2 and 26.3 - which costs the depth write (clouds/water paint over the backdrop again, but only with shaders on) and guarantees the box and the letters can never disagree about being drawn. `labelBackdrop(shaderPackActive)` picks between that and the depth-writing private pipeline. Every version renders in 3D world space through `LevelRenderer`; there is no HUD-space rendering anywhere in this mod.
- **Depth state is intentionally identical between versions, and the tradeoff it carries is accepted, not overlooked.** In all three versions, every *custom* pipeline in `WaypointRenderTypes` — the marker always, and the vanilla-mode backdrop — uses `DepthStencilState(CompareOp.ALWAYS_PASS, /*write=*/true)`: never occluded by solid terrain (the test always passes), but leaving a real depth value at their own (deliberately near, ~4 block) projected distance, routed to `OutputTarget.WEATHER_TARGET` on 26.1 and 26.2 — 26.3 deleted that enum, see the last paragraph here. See `MARKER_PIPELINE`'s javadoc in either version for the full story, summarized here because the reasoning spans a real regression that was found, reverted, and then deliberately reinstated:

  The depth write exists to solve one real problem — Minecraft renders clouds and translucent terrain (water) into their own render target and composites it back over the main target afterward using depth, so a pipeline that never writes depth (vanilla's own see-through text types included) leaves nothing there for that composite to test against, and clouds/water painted later in the frame simply draw over the marker/label regardless of how close they actually are. Routing the write to `OutputTarget.WEATHER_TARGET` instead of the default main target avoids a *second* problem the write itself causes: water renders into its own translucent target, which starts each frame as a straight copy of main's depth buffer, so a near depth value written into main gets copied there too, and water then depth-tests itself against a "wall" a few blocks away and loses — it simply never draws where the marker/label sits, revealing whatever solid terrain is behind it.

  Both of those targets, and the cross-target depth-sorted composite that lets a weather-routed draw beat translucent water in the first place, only exist when Minecraft's own multi-target transparency compositor is running — gated behind `OptionsRenderState.improvedTransparency`, vanilla's **"Fabulous!"** graphics setting, confirmed by reading the deobfuscated 26.1.2 and 26.2 client jars: outside Fabulous, `LevelRenderer` never allocates a separate weather target at all, and `OutputTarget.WEATHER_TARGET.getRenderTarget()` silently falls back to the *default main target* — the one the routing exists to avoid — the moment that target is absent. On "Fancy" (vanilla's default) this makes the whole `WEATHER_TARGET` maneuver a no-op that still writes a near depth value straight into main, reproducing the water-hole bug it was meant to prevent. This was caught, not theorized: reported against 26.2 running Sodium (which reimplements the exact `LevelRenderer` code path this reasoning depends on, so its behavior here isn't verifiable from this codebase) with Fancy graphics.

  For one session 26.2 gave up the depth write entirely for the vanilla-mode marker/backdrop instead, matching what vanilla's own see-through text has always done (confirmed via bytecode: `RenderPipelines.TEXT_SEE_THROUGH` declares no `DepthStencilState` at all) — renderer-agnostic by construction, behaving identically under vanilla, Sodium, Fabulous, or Fancy, at the cost of reintroducing the original clouds/water-paint-over-the-marker bug (the one the depth write exists to fix) unconditionally in 26.2's vanilla mode. That tradeoff was tried and explicitly rejected on 2026-08-24: a label that constantly looks like it's underwater the moment any cloud or water is nearby was judged worse than an occasional, localized hole in water immediately around a waypoint outside Fabulous — most waypoints are not placed inside or right at a water body, so the hole case is rare where the paint-over case is not. 26.2 was reverted back to the shared depth-write + `WEATHER_TARGET` pipeline, matching 26.1's behavior, and 26.2's javadoc now documents the Fabulous-gating limitation and the Sodium report directly instead of treating it as an open question — 26.1's own javadoc was deliberately left as it was (it already worked, and was never touched during the investigation), so it still doesn't spell out the same caveat in writing even though it carries the identical, already-shared tradeoff. The shader-mode paths in every version (`BEACON_PIPELINE`/`BEACON_MARKER`, and 26.2's and 26.3's `SHADER_BACKDROP` riding vanilla's own depth-testing `textPolygonOffset`) are untouched by any of this — see `LABEL_PROJECTION_DIST` above for why the shader-mode label is safe from the same close-block occlusion problem in a different way.

  **26.3 keeps the write and loses the routing, because 26.3 deleted the machinery the routing steered around.** `OutputTarget` does not exist there, and `RenderSetup.RenderSetupBuilder` has no `setOutputTarget` — it has `setOitPipelines(OitPipelineSet)` instead. The multi-target transparency compositor was replaced by real order-independent transparency (`net.minecraft.client.renderer.oit`, with `OitStage.DEPTH_BOUNDS`/`TRANSMITTANCE`/`ACCUMULATE` and an `OitPipelineSet` on each translucent render type: `OIT_TERRAIN`, `OIT_CLOUDS`, `OIT_WEATHER`, `OIT_TEXT`…), still gated behind the same `OptionsRenderState.improvedTransparency` — "Fabulous!" — which now selects OIT rather than target compositing. With no weather target to route to, 26.3's marker/backdrop pipeline writes its near depth into the main buffer. Read against 26.2's own javadoc that is not a new tradeoff but the same one with its condition removed: outside Fabulous, `WEATHER_TARGET` already falls back to the main target, so 26.1/26.2 write into main for most players already, and the localized hole in water immediately around a waypoint is the cost that was weighed and accepted on 2026-08-24. 26.3 makes that the unconditional case. Vanilla's see-through text is still the no-write alternative (26.3's `TEXT_SEE_THROUGH` is literally `withDepthStencilState(Optional.empty())`, confirmed from `RenderPipelines`' bytecode), and dropping to it is still the one-line change if the hole ever proves worse than the paint-over here — but it would reintroduce exactly the bug the write exists to fix, which is why it was not the default. This is the one claim in this section read off the API surface rather than watched happening: the 26.3 dev client renders markers and labels correctly (verified through `runClient`), but not specifically against water under Fabulous.
- `ShaderDetector` detects an active shaderpack via reflection (tries modern Iris, then legacy Oculus/Iris, then OptiFine; returns `false` with no exception if none are present), caching the result for 1 second.

### UI

Hand-built on vanilla `Screen`, no third-party UI toolkit. Shared widget is `ModernButton` (fluent builder: `ModernButton.modernBuilder(...).pos(x,y).size(w,h).build()`), with normal/hover/disabled states in a near-black translucent palette centralized in `UiPalette` (color constants only, no Minecraft imports, so it stays trivially byte-identical across versions). GUI icons under `textures/gui/` are drawn as plain white masks and tinted at draw time via `Icons`' `drawMarkerIcon`/`drawPortalIcon` helpers and the tinted 11-arg `GuiGraphicsExtractor.blit(..., int color)` overload (multiplicative: `result = texture × color`), rather than baking color into each PNG — this is also how the waypoint-list marker swatch and the focus button get colored with the waypoint's own ARGB color instead of drawing a flat `fill()` square. Three screens:
- `WaypointCreateScreen` — create/edit modal (name, X/Y/Z, two-bar color picker, dimension-share toggle, Enter-to-save). The palette data and its random-pick helper (`WaypointColors.random()`, the screen's own starting selection) live in `WaypointColors` rather than here, extracted once Fast Ping needed the same colors with no picker UI to offer one through. The same constructor path is used to pre-fill coordinates from the player's feet (`N` key) or from a crosshair raycast (`H` key, see `WaypointPing`) — the screen itself is agnostic to where the `BlockPos` came from. `key.easywp.fast_ping` bypasses this screen entirely (see Keybindings above).

  **The color picker has gone through four designs across this project's git history, each correcting something the previous one got wrong.** The original was a flat 15×4 grid (60 colors: grayscale + 14 hues, × vivid/light/deep/dark). That grid was *densified* to 28×7 (196 colors) by inserting an RGB midpoint between every adjacent pair of hues and shades, on the theory that "similar colors near each other" meant making the whole grid one continuous gradient - which instead made most of it near-duplicate shades of the cell right next to it, worse at the one thing a picker has to do well: letting the player tell two colors apart at a glance. That was replaced by 20 maximally-distinct base colors (18 hues 20° apart + white + black) in a 4×5 grid, paired with a second, smaller grid showing 7 shades of whichever base was active - better separated, but the two grids side by side read as loosely related rather than as one control, the "active family" indicator borrowed the same gold used elsewhere for a focused waypoint (a collision in meaning), and 7 shades was thin for a real dark-to-light ramp.
  
  **The current design (`WaypointColors.FAMILY_BAR`/`HUE_FAMILIES`/`GRAYSCALE_FAMILY`) is two touching horizontal bars, stacked, framed separately.**
  - **The top bar is 14 family colors: 12 hues spaced exactly 30° apart around the color wheel (12 × 30 = 360, dividing evenly, same reasoning as the 18-hue version's 20° spacing but wider so the hues read as more obviously distinct - a direct response to the 20-base design's hues still doubling up visually) plus white and black.** `WHITE_INDEX`/`BLACK_INDEX` are the two flat indices (12, 13) past the 12 hues. The 14 swatches sit flush against each other, no gap - `FAMILY_SWATCH_W` is `PICKER_WIDTH` (210) divided evenly by 14 (15px each). Each hue swatch is `HUE_FAMILIES[i][6]`, not the fully saturated, fully bright vivid tone at index 7 - full brightness at full saturation is the single "loudest" point on the whole ramp, and 12 of them side by side read as garish rather than as a calm set of families to choose from. One step back (still full saturation, brightness pulled in by about an eighth) keeps each hue clearly identifiable without going far enough to look muddy. White and black are left at their own extremes, since neither is a saturated color with a "loud" version to soften.
  - **The bottom bar is `WaypointColors.SHADE_COUNT` (15) shades of whichever family is active, also touching, strictly dark (left) to light (right).** Each hue's row is built as two halves meeting at the middle index: index 0..7 darkens toward the vivid tone by raising brightness at full saturation (shades, mixing in black), index 7..14 lightens past it by lowering saturation at full brightness (tints, mixing in white) - so the vivid tone anyone would call "the" red/blue/etc. sits exactly in the middle, not smeared across a whole plateau. `SHADE_SWATCH_W` is the same 210 divided evenly by 15 (14px each) - the two bar widths agreeing on 210 rather than one deriving from the other is what keeps them the same total width without either one picking an odd swatch size to make it work. White and black share one family: the plain grayscale ramp (dark to light, same direction as every hue row), since neither has a hue of its own to shade or tint.
  - **`BAR_HEIGHT` (15) matches `FAMILY_SWATCH_W` exactly** - the top bar's swatches are square, and the bottom bar's own 14px-wide ones are one pixel off square, close enough to read as the same shape. (An intermediate value of 17 was tried first and judged still too tall to read as "almost square.")
  - **Touching swatches change how selection has to be drawn.** A swatch with no gap on either side can't take an *outer* ring the way the previous designs' spaced-out swatches could - it would paint over the neighboring color. `drawColorSwatch` instead fills the whole cell edge-to-edge with no inset in the normal case (so the bar reads as one continuous strip), and draws the selection mark as a 2px inset frame when it's the exact selected color.
  - **Every accent border in the picker is the same fixed `UiPalette.MODAL_BORDER` color** - the exact-selection frame on either bar, and the "this family is active, but not the exact selection" mark on the top bar, all draw in it, and so does the frame around each bar. Two earlier attempts used white for the selection frame and a separate blue (then briefly gold, which collided with the unrelated meaning `FOCUS_OUTLINE_ON` already carries elsewhere in this UI - a waypoint's own *focused* state) for the active-family mark; a highlight whose color depended on which of the two states was showing read as inconsistent. Tying every one of them to the same constant the bars' own frame already uses means the picker's accent color literally cannot drift out of sync with itself again.
  - **Each bar gets its own 1px border frame, 2px outside its own bounds, filled before the swatches are drawn on top of it.** With no internal gaps left inside either bar to hint that "this is one control," and both bars sitting one above the other, the frame plus the gap between them is what keeps a player from reading the whole thing as a single undifferentiated block of color.
  - **Clicking a top-bar swatch selects it outright and switches the bottom bar to that family; clicking a bottom-bar shade changes the selected color without changing which family is shown** - `activeBaseIndex` (which family the bottom bar is browsing) and `selectedColor` (what will actually be saved) are deliberately two separate pieces of state, because after picking a shade they disagree on purpose: the active family's own top-bar swatch is not necessarily the selected color anymore.
  - **The bottom bar's `SHADE_COUNT` buttons are created once and never rebuilt when the active family changes.** Each one closes over its own fixed slot index and looks up `WaypointColors.familyOf(activeBaseIndex)[slot]` at click time rather than capturing a color value at creation time; the render loop does the same lookup every frame. Switching families is therefore just mutating `activeBaseIndex` - no widget list surgery, unlike `WaypointListScreen`'s `refreshItemWidgets()` pattern used elsewhere in this codebase for a dynamic row count.
  - **`WaypointColors.nearestMatch(int)` is what makes editing an existing waypoint (or Fast Ping's own `random()` pick) show a coherent picker state**, since a waypoint's stored color need not be exactly one of the palette's own values - an older save file, or a color from before this redesign. It searches every shade of every family for the nearest RGB match, not just the 14 top-bar entries, specifically so a waypoint saved deep in a hue's dark end still activates *that hue's* family instead of the objectively-closer-in-raw-RGB-terms black.
- `WaypointListScreen` — searchable/paginated list with per-row TP/focus/show-hide/edit/share-to-chat/toggle-shared/delete actions; TP is gated on `Permissions.COMMANDS_GAMEMASTER`. Row order is driven by `WaypointSortMode`, cycled with the button beside the search box and persisted in `ModConfig.list.sortMode`; its default `CREATED` deliberately performs no sort at all, since waypoints are appended on creation and reloaded in the same order, so insertion order already is creation order. Sorting is applied when the list is rebuilt, not per frame, so `DISTANCE` does not reshuffle rows while the player walks. The action-icon strip is built right-to-left from `centerX + 120`; TP is the one *conditional* icon in it (gated on the permission above) and is deliberately the innermost (`centerX + 20`), so every icon's position stays fixed regardless of whether the player has the permission — `NAME_MAX_WIDTH` is sized against that inner edge. Copying a row's coordinates is a double-click on **either** the name or the coordinates text - `nameOrCoordsRowAt()`'s hit box spans both lines (`itemY` to `itemY + 21`), not just the coordinates' own line, since a player reaching for the row has no reason to aim at the bottom half specifically. Not a dedicated button: the modal is only 290px wide and the icon strip already sits within 7px of its edge, with no room for an eighth icon. An 18x18 `copy.png` + `Icons.COPY` button was tried first and reverted for exactly that reason. The double-click itself is hand-timed (`COORDS_DOUBLE_CLICK_MS`, 250ms) rather than trusting the `doubleClick` boolean `mouseClicked(MouseButtonEvent, boolean)` receives - confirmed from `MouseHandler`'s own bytecode that the one call site reaching a `Screen` subclass's override always passes a literal `false`; real double-click detection lives deeper inside `Screen`'s default widget-dispatch logic, which an override of this method bypasses entirely. Feedback on a successful copy is an inline `"Copied!"` (`easywp.list.coords_copied`, now just that word - no longer a full sentence) drawn in `UiPalette.TEXT_SUCCESS` right after the coordinates text itself, for `COPIED_FEEDBACK_MS` (1000ms) - not the action-bar overlay message every other mutating action uses, because this one is meant to be read beside the thing it confirms, not glanced at in the HUD. Three buttons sit *outside* the modal, anchored to the screen's own bottom corners rather than to the panel: the config gear on the left, and — only when Xaero's Minimap is installed — the Import/Export pair on the right (see Xaero's Minimap integration below). That is the only place left with room for a button without shrinking something, and it keeps them from moving when the modal's contents change.

  **Sharing to chat cannot carry color, and that is a vanilla limitation, not a missing feature here.** The non-Xaero share format is `NAME --> DIMENSION X Y Z` (`easywp.share.chat`), sent via `ClientPacketListener.sendChat(String)` - a real chat message, indistinguishable from one the player typed. Vanilla strips the section sign from chat text a player sends before broadcasting it, a long-standing anti-spoofing measure with no client-side opt-out, so no client mod - this one included - can make the dimension word render in `DimensionNames.color()`'s green/red/purple for *other* players reading it in chat. The format still encodes the dimension as plain text at a fixed position, which is the most useful approximation reachable without a server-side companion or falling back to the Xaero-recognized line (`xaeroChatFormat`, unaffected since that one is parsed and re-rendered by Xaero's own client, never shown as raw chat text).
- `ModConfigScreen` — mod settings, built on vanilla's own `OptionsSubScreen` + `OptionsList` (the same scrollable widget Minecraft's Video Settings/Controls screens use) rather than `ModernButton`, so it looks and scrolls like a native options screen. One setting per row (control + its own "Reset" button), grouped under section headers, backed by `ModConfig`. Three things about inheriting from vanilla here are easy to get wrong:
  - **`OptionsSubScreen.list` is null until `init()` runs.** It is declared `@Nullable` and only assigned inside `addContents()`, which `init()` calls — and `init()` is called by `Minecraft.setScreen`/`setScreenAndShow`, not by the constructor. Every "Reset" button and the ping follow-render-distance toggle go through `reopen()`, which rebuilds the screen to pick up the new value; it must therefore set the new screen **first** and restore the carried-over scroll position **after**, or it dereferences null. (It did exactly that until 2026-08-28, so every Reset click crashed the game.) Setting it first is also what makes `setScrollAmount` meaningful — it clamps against `maxScrollAmount()`, which is 0 on a list that has not been populated yet.
  - **`removed()` is overridden to do nothing**, on purpose: `OptionsSubScreen`'s default re-saves vanilla's own `options.txt` on close, which this screen never touches.
  - **`addContents()` is overridden rather than inherited** so the `OptionsList` can be constructed with `LIST_WIDTH` (330) instead of the full screen width. `OptionsList.getRowWidth()` is hardcoded to 310 and the scrollbar sits at `getRowRight() + margin`, so passing the window width would strand the scrollbar at the far right edge, nowhere near the rows.

Related classes not previously listed here: `ModConfig`/`ModConfigScreen` (settings, see Persistence above), `WaypointDisplayMode` (the visibility-cycle enum driving the toggle key), `WaypointRenderTypes` (per-environment marker `RenderType` selection, see Rendering above), `DimensionNames` (dimension id → tab header/chat name/pretty name/accent color/shared-conversion-eligibility, extracted out of `WaypointListScreen` once a second caller needed the same mappings — no Minecraft imports, stays trivially identical across versions like `UiPalette`/`Icons`), `ImportWorldScreen` (the cross-world waypoint import picker reached from `ModConfigScreen`'s "Import" section, see Persistence above for what "import" means and why the row it lives on is `addSmall` rather than `addBig`).

### Death waypoints

`DeathWaypointManager` needs no mixin: it watches `player.getHealth()` across client ticks and treats the alive→dead edge as the death, which is safe because the death location does not change until the respawn packet arrives. On that edge it creates a black, non-shared waypoint named from `easywp.death.name` plus the local `HH:mm`, after evicting the oldest existing death waypoints down to `ModConfig.deathWaypoints.maxCount - 1` (default `maxCount` is 1, which reproduces the original "only the latest death is kept" behaviour).

Deletion is a dwell timer, not a proximity trigger: a death waypoint is removed once the player has stayed within `radius` of it, in the same dimension, for `graceSeconds` **without leaving** — stepping out resets the timer. Each death waypoint keeps its own timer in a `Map<Waypoint, Long>`, so with `maxCount > 1` the player can walk through several and each expires on its own schedule; `dwellStart.keySet().retainAll(...)` drops timers for waypoints that were deleted or evicted meanwhile. Two deliberate details: arrival checking is skipped entirely while dead (the player does not control movement on the death screen, so sitting on the corpse before respawning must not count as arriving), and the manager calls `WaypointRenderer.checkAndLoadWorldWaypoints()` itself each tick, because the renderer skips that reload while display mode is `DISABLED`. Editing a death waypoint in `WaypointCreateScreen` clears its `death` flag, promoting it to a permanent waypoint so it stops being auto-deleted.

### Xaero's Minimap integration

easyWp can copy its own waypoints into [Xaero's Minimap](https://modrinth.com/mod/xaeros-minimap) (whose waypoints Xaero's World Map merely *displays* — it has no waypoint store of its own, so there is nothing to integrate with there directly) and copy Xaero's back. `xaerominimap` is a genuine `clientCompileOnly` dependency (not reflection — see `XaeroBridge` above), pinned per version in each `gradle.properties` — `26.5.0` for 26.1 and 26.2, `26.5.1` for 26.3, which is the only release published for it — from Xaero's own maven, which publishes Mojang-mapped jars per Minecraft version (`xaerominimap-fabric-26.1.2`, `xaerominimap-fabric-26.2`, `xaerominimap-fabric-26.3`) rather than the intermediary-mapped jars their public dev docs describe for `modImplementation` — confirmed by disassembling the jar's own bytecode, which references real names like `net/minecraft/resources/Identifier` directly, not obfuscated `class_NNNN` ones. That is what makes a plain `clientCompileOnly` dependency (no `mod*` configuration, matching how this project already declares Fabric API - see Entry points) link correctly against this project's own Mojmap-compiled code.

**Nothing in this integration runs on its own.** The whole surface is two buttons — `XaeroSync.importNow()` and `exportNow()` — wired to the pair in the bottom-right corner of `WaypointListScreen`. An earlier version pushed on every `saveToFile()`, imported on every world join, and polled `WaypointSet.size()` **every client tick** to pick up Xaero-side edits within ~50ms. All of that is gone: two lists that silently rewrite each other are hard to reason about, and everything the poll existed for a button press covers without needing an event Xaero doesn't expose anyway.

**Each button makes the target match the source — but only for waypoints the two have actually exchanged.** A sync adds what the source has and the target lacks, *and* removes what the target still has but the source has deleted. That removal is deliberately narrow: it only ever touches a waypoint recorded in `XaeroLinkLedger` as having existed on **both** sides. So a Xaero-only waypoint survives any number of Exports, an easyWp-only waypoint survives any number of Imports, and the player's two lists never clobber each other's private entries. Since identity is name + position, a *move* or *rename* in the source reads as a delete plus an add, so edits propagate too — not just creations and deletions.

**`XaeroLinkLedger` has to be persisted, not derived, and that is the crux of the feature.** It stores one identity per line that the two sides have exchanged, per world, at `config/easywp/xaero_links_<worldId>.json`. The reason it can't be computed on the fly: the moment the player deletes a waypoint in easyWp, nothing in the *current* contents of either list distinguishes "Xaero's copy of the thing I just deleted" (which Export should remove) from "a waypoint of Xaero's that easyWp never had" (which Export must not touch). The ledger is that distinction, written down before it's lost. It is read and written fresh on each press rather than cached — a handful of presses per session makes two small file operations free, and having no state means there is no per-world invalidation to get wrong on a dimension change or server switch. Losing or corrupting the file fails safe: an unreadable ledger reads as "nothing has ever been synced", which makes both buttons purely additive again, so it can leave a stale copy behind but can never delete something it shouldn't. `JsonStore` gives it the same atomic write + `.bak` recovery as the waypoint store.

**"Couldn't read" is never treated as "empty", and that guard is the one thing standing between this feature and real data loss.** Every read of the other side can come back `null` — no minimap session (main menu, between world loads), or a `waypoints.txt` that isn't where `guessedFile` guessed. If that were collapsed into an empty list, every linked waypoint would look deleted and a single click would wipe everything the two sides had ever shared. So `XaeroBridge.readRealWaypoints` returns `null` for "could not ask" versus an empty list for "asked, Xaero has none here", and a dimension that reads `null` is skipped whole: no adds, no removes, and **its ledger entries left exactly as they were**. The per-dimension granularity matters for the same reason — one unreadable dimension keeps its history while the rest of the sync proceeds. A dimension whose write fails is skipped the same way, so its ledger never claims a sync that didn't happen.

Two smaller pieces of the delete half are easy to get wrong:
- **Export visits every dimension in the ledger, not just the ones easyWp currently has waypoints in.** Delete the last easyWp waypoint in the Nether and the Nether vanishes from `groupByTargetDimension()` entirely — visiting only that map would leave its shared Xaero copies behind forever, which is precisely the deletion the button is for.
- **Import removes an easyWp waypoint only when *all* of its projected positions are gone from Xaero.** A `shared` waypoint is one easyWp waypoint with two images in Xaero (native + the 1:8 converted one); deleting just one of those images is an edit to the mirror, not a request to delete the waypoint. `XaeroSync.deletedOnXaerosSide` requires "was linked", "every projection's dimension was readable", and "no projection still present".

The old `Waypoint.fromXaero` flag is still gone, and is not what came back here: it marked *which* easyWp waypoints an automatic import had created, living on the waypoint and therefore dying with it — useless for Export, which needs the link to outlive the easyWp waypoint's deletion. That is the whole reason the ledger is a separate, waypoint-independent file.

**Export writes the player's own real waypoints, and that is a deliberate change from what it used to do.** The earlier version pushed into Xaero's `ThirdPartyWaypointManager`/`ThirdPartyWaypoints` layer — an API built for a mod to contribute map markers without touching anything the player placed by hand, which sounds like the safe choice and was the wrong one for this feature: that layer is pure runtime state Xaero never persists, so an exported waypoint **vanished on the next restart** and was drawn as a separate overlay rather than appearing in the player's own waypoint list at all, which is what "export to Xaero" has to mean. `XaeroMinimapBridge.addRealWaypoints` instead follows the sequence read from Xaero's own `xaero.hud.minimap.waypoint.DeathpointHandler.createDeathpoint` (the same problem: Xaero adding a real waypoint programmatically and needing it to survive a restart): resolve the dimension's `MinimapWorldContainer` the same way as before (`BuiltInHudModules.MINIMAP.getCurrentSession()` → `.getWorldManager().getAutoRootContainer()` → `.addSubContainer(...)`, per-dimension via `MinimapDimensionHelper.getDimensionDirectoryName(ResourceKey<Level>)`), then `world.getCurrentWaypointSet()` → `set.add(waypoint)` → `session.getWorldManagerIO().saveWorld(world)`. Four details there are bytecode-confirmed, not guessed, and each would be a silent bug if assumed:
- `saveWorld` declares a **checked `IOException`**, so it is caught inside `XaeroMinimapBridge` rather than at `XaeroBridge`'s edge, whose catch only covers `LinkageError | RuntimeException`. A failure there returns -1, which is what sends the caller to the file fallback — the waypoints are already in Xaero's in-memory set either way, so they are visible for the session regardless.
- `WaypointSet.add(wp, true)` **prepends**; the single-argument `add` appends. Export uses the latter, or easyWp's whole list would be inserted above the player's own waypoints in reverse order.
- `MinimapWorldContainer.addWorld(String node)` is get-or-create, and the right node name for a dimension with no world yet is `"waypoints"` — `MinimapWorldManagerIO.getWorldFile` derives a world's file name from its node and `loadDimensionFolder` names a node after the file it loaded, so that node is exactly the `waypoints.txt` Xaero itself would have written.
- The set to write into is whichever one is current, and `XaeroWaypointFormat.DEFAULT_SET_NAME` (`"gui.xaero_default"`, from `MinimapWorld.DEFAULT_SET`) is its name for the file fallback's `set` field. A set name Xaero doesn't have would still parse, but the waypoints would sit in a set the player has to go find before seeing any of them.

`XaeroMinimapBridge.applyRealWaypoints` does one dimension's adds and removes together, and three things there are each a bug done the obvious way: removals are collected during the `getWaypoints()` walk and applied strictly **after** it exits (`WaypointSet.remove` mutates the very list being iterated, so removing in place throws `ConcurrentModificationException` instead of removing); removals sweep *every* `WaypointSet` of every `MinimapWorld` in the dimension, because that is where `readRealWaypoints` found them and a waypoint the player filed in their own set must still be removable, while additions only ever go into the *current* set; and each changed world is saved exactly once, with the touched set collected rather than assumed to be one, since removals can land in a different world from additions.

All identity comparisons — the ledger, both dedups, and the removal match on both the live and file paths — use **name + X + Z**, deliberately ignoring Y: `readRealWaypoints` reports a synthetic `y = 64` for an Xaero waypoint saved without one (`isYIncluded()` false), so comparing Y would make those never match, duplicating on every Export and never matching on a removal. `XaeroWaypointFormat.removeAll` uses the same rule (`sameColumn`) rather than `merge`'s own `sameSpot`, which does include Y — the two would otherwise remove different things for the same click depending on whether the live bridge happened to be usable.

**The `waypoints.txt` file is the fallback, never a second writer.** Each operation decides *per dimension* whether the live bridge could actually do the work; only if it couldn't (Xaero missing, a binary-incompatible version, no active session, or its own `saveWorld` failing) does this write the file directly, as `removeAll` then `merge` in one write — never both paths for the same dimension, which is what avoids the real failure mode this split exists to dodge: Xaero rewriting its own `waypoints.txt` on save and clobbering a concurrent write from this mod. `merge` rather than the `replaceSet` the old continuous sync used: a sync's add half is exactly add-only and idempotent, and the delete half is now explicit in `removeAll` instead of implied by replacing a whole set. `replaceSet` was deleted along with the sync it existed for — it had been the production path and `merge` the tested-but-unused one, and that is now the other way round. `XaeroWaypointFormat`'s 14-field line layout (`waypoint:name:initials:x:y:z:color:disabled:type:set:rotate_on_tp:tp_yaw:visibility_type:destination`) and its 21-entry color palette (index = Xaero's own `WaypointColor` ordinal, used by both the live bridge and the file) were both read from `xaero.hud.minimap.waypoint.io.WaypointIO`'s disassembled bytecode, not guessed from third-party descriptions of the format (which disagree with each other and describe an older version — notably, the per-dimension folder name is `<namespace>%<path>` with `/` also replaced by `%`, not the `dim%N` scheme older write-ups describe; `XaeroSync.dimensionFolderName` reproduces that exactly, confirmed the same way). The one thing that genuinely isn't confirmed, because there is no live bridge to ask on this fallback path by definition, is the *world root* folder name (`Singleplayer_<name>`/`Multiplayer_<ip>`) — a standard, widely-documented guess rather than a bytecode-confirmed one; a wrong guess there costs nothing but a missed write, since easyWp's own JSON store remains the source of truth regardless.

**`XaeroBridge` is the only class allowed to be a no-op on Xaero's absence *or* its incompatibility**, and treats those as genuinely different failures — `isModInstalled()` and `isAvailable()` are therefore two different questions, not one with a convenience alias. `isModInstalled()` is just `FabricLoader.isModLoaded("xaerominimap")` (Xaero not installed at all — nothing in `XaeroMinimapBridge` is ever touched, so no `xaero.*` class is even resolved) and is what decides whether the Import/Export buttons appear. `isAvailable()` additionally requires a usable bridge, and is what decides whether an operation goes live or falls back to the file. The second failure is the one a compiled dependency has that reflection never did: the player can run an *older or newer* Xaero than the `26.5.0` this was compiled against, and a mismatched release missing a method/field this code calls produces `NoSuchMethodError`/`NoClassDefFoundError` — both `LinkageError`, which a plain `catch (Exception)` does **not** catch. Every public method on `XaeroBridge` therefore catches `LinkageError` as well as `RuntimeException`, logs once per session (not once per call), and disables the bridge for the rest of the session rather than retrying a failure that a version mismatch will reproduce identically every time. `disable()` deliberately does **not** clear the cached `modLoaded` — it once did, which meant an incompatible Xaero release made the mod look uninstalled, hiding the buttons in precisely the situation the file fallback exists for and making it unreachable.

**Import reads the player's own real waypoints**, manually created *or* landed via a chat-shared `[Add]` button someone clicked, from a `MinimapWorld`'s `WaypointSet`s (`XaeroMinimapBridge.readRealWaypoints`), skipping `isTemporary()` ones the same way Xaero's own `WaypointIO.saveWaypoints` excludes them from its file — they are pings and one-off destinations, not something the player asked to keep. It scans every known dimension (the vanilla three, plus anything easyWp already has waypoints in, plus wherever the player is), reading every one of them **before** mutating anything, since the removal pass has to judge each easyWp waypoint against the whole picture including the dimensions its shared twin projects into. The button calls `refreshItemWidgets()` afterwards because the screen only rereads the list when something tells it to — the change would otherwise stay invisible until the next keystroke or dimension switch.

**`XaeroSync.alreadyHasSimilar` compares against projected positions, not just native ones, and that is load-bearing.** A `shared` easyWp waypoint is exported into both Overworld and Nether, at each one's own 1:8 converted position (`forEachTarget`, the third copy of that projection in this codebase). A later Import reads the Nether copy back, and matching only native positions would not recognise it as the Overworld waypoint it came from — so **every export→import round trip would add a spurious Nether duplicate of every shared waypoint**. Iterating `forEachTarget` over each existing waypoint is what closes that.

`ModConfig.XaeroIntegration` holds just `enabled` (default `true`) and `xaeroChatFormat` (default **`false`**); `pushOnChange`, `autoImport` and `writeFiles` went with the machinery they configured — there is nothing periodic left to switch off, and the file fallback is no longer a choice but what happens when the live path can't run. `enabled` is a pure master switch: it decides whether the two buttons appear at all (alongside Xaero being installed) and whether either action does anything. It is a group added whole, for the field-initializer-vs-Gson-zero-value reason noted in Persistence above. Note the asymmetry that rule creates when a default is *changed* rather than added: `xaeroChatFormat` flipped from `true` to `false`, but a `config.json` that already carries the key keeps whatever it saved — only a fresh config, or one missing the whole group, picks up the new default.

**Both Xaero config rows are greyed out when Xaero isn't installed**, via `ModConfigScreen.gated(...)`, which clears `active` and attaches a `Tooltip` explaining why (`easywp.config.xaero_missing`). The section header stays visible so the integration is still discoverable; what it avoids is a live toggle that silently changes nothing, which reads as a bug rather than as an unmet requirement. Vanilla's own options widgets already grey their label out when inactive, so no custom drawing is involved.

The waypoint-list share button's chat message goes through `I18nHelper`'s `easywp.share.chat` key instead of a raw, untranslated `String.format` - a real bug independent of this feature, fixed in passing - formatted as `NAME[x, y, z] -> Dimension`. With `xaeroIntegration.xaeroChatFormat` on (not the default) it goes through `XaeroWaypointFormat.chatShareLine` instead, producing the `xaero-waypoint:` line Xaero's own chat listener recognizes on a recipient's end and offers an `[Add]` button for. That one is opt-in rather than default precisely because a recipient *without* Xaero sees the raw tag string instead of a readable sentence, and most recipients are in that position. Clicking `[Add]` is handled entirely on Xaero's side and lands in Xaero's own list; reaching easyWp's list then takes an Import click, where it used to be picked up by the poll.

**The two buttons sit in the screen's bottom-right corner, mirroring the config gear in the bottom-left** — same 20x20 `ModernButton`, same 8px margin, and like the gear they are anchored to the **screen** rather than to the modal, so neither moves when the modal's contents do. Import is the inner one, Export the outermost (`xaeroButtonX(1)`/`xaeroButtonX(0)`). They are created in `init()`, not `refreshItemWidgets()`, since nothing about them depends on the list contents, and gated on a `showXaeroButtons` field resolved once per `init()` and read by both the widget creation and the glyph drawing so the two can never disagree about whether the buttons exist. Their glyphs (an arrow onto/off a bar — the universal download/upload pair, the bar being what distinguishes them from the bare scroll arrows) are hand-drawn with `fill` rather than added as texture assets, the same choice `drawSortIcon` already documents for the same reason: one size, one colour pair, no asset worth the round trip. Being icon-only they carry a real `setTooltip(Tooltip.create(...))` — `AbstractWidget.setTooltip` exists in all three versions and `AbstractWidget.extractRenderState` calls `refreshTooltipForNextRenderPass` itself, so `ModernButton`'s own override of the contents hook doesn't bypass it. Deliberately **not** duplicated into `ModConfigScreen`, where an earlier Import/Export action row lived: two places to click for the same thing, with nothing to tell the player which.

**The chat-share line is a genuinely different field layout from the file line, not the same one with a different tag - this was a real bug, not a hypothetical one.** An earlier version of `chatShareLine` built it by slicing `serialize`'s file-line output, on the assumption the two formats matched past the tag; they coincidentally have the same field *count* but diverge in meaning from field 7 onward, so the line parsed on Xaero's end without throwing but behaved wrong, and `[Add]` silently did nothing. Disassembling `WaypointSharingHandler` (both the outgoing `StringConcatFactory` recipe in `onShareConfirmationResult` and the validating parser in `onWaypointAdd(String[])`) turned up the real layout - `name:initials:x:y:z:color:rotation:yaw`, with an optional 9th "destination details" field - and, critically, that the 9th field is not just unused but actively harmful to include: `onWaypointAdd` only attempts to resolve a destination world when the split array has more than 9 elements, falling back to "the receiving player's current world" otherwise, which is exactly what a shared waypoint should do. The earlier bug sent this mod's own Xaero waypoint-set name in that slot; since it was neither the literal `"External"` nor an `"Internal-<matching path>"` token Xaero recognizes, the receiving parser failed to resolve a destination, logged one line to Xaero's own client log, and added nothing - no exception, no chat error, nothing visible to either player, which is exactly why this took three rounds of "the Add button still doesn't work" to actually pin down instead of surfacing as an obvious crash.

### i18n

All translated text — UI strings and keybinding names alike — lives in the lang JSONs under `common/src/main/resources/assets/easywp/lang/`, so a new language is one new file and no code. `I18nHelper` used to hold the UI strings itself, in a hand-written `switch` duplicated across both version trees; it is now a one-method bridge that prefixes a short key with the `easywp.` namespace and returns `Component.translatable`. Keys stay short in Java (`menu.title`, `sort.name`) and namespaced in the files (`easywp.menu.title`) — unprefixed keys would collide with vanilla and other mods in the global translation registry. `WaypointSortMode` and `WaypointDisplayMode` return those same short keys from `getTranslationKey()`.

Three things about the lang files are not obvious and will silently break text if ignored:

- **Regional locale codes are resolved by exact match, no fallback chain.** `LanguageManager.onResourceManagerReload` builds a two-entry list — `en_us`, then whatever the client's exact selected code is (`es_mx`, `es_ar`, ...) — and hands it to `ClientLanguage.loadFrom`, which loads `lang/<code>.json` per namespace and silently skips it if that exact file is absent for that namespace (logged as "Skipped language file", not an error). There is no `es_mx` → `es` → `en_us` cascade: a player on any Spanish variant other than `es_es` falls all the way back to English for this mod's strings unless that exact file exists. Confirmed against Mojang's own asset index, Minecraft ships seven Spanish locale codes (`es_ar`, `es_cl`, `es_ec`, `es_es`, `es_mx`, `es_uy`, `es_ve`), so all seven ship here, all identical in content to `es_es.json` — reproducing what the old `I18nHelper.isSpanish()`'s `code.startsWith("es_")` used to do for free. A new Spanish-family locale Mojang adds later needs its own duplicate file for the same reason.

- **The format specifiers are not `String.format`'s.** Minecraft's translation formatter accepts only `%s` (and positional `%1$s`), plus `%%` for a literal percent. A `%d` or `%.1f` raises `TranslatableFormatException` — caught by vanilla, so the raw untranslated string is displayed — and a bare `%` raises an `IllegalArgumentException` that vanilla does **not** catch. Numbers needing a fixed number of decimals are therefore formatted by the caller and passed as strings; `ModConfigScreen.ConfigSlider` takes a `decimals` argument for exactly this, which is why its labels read `Size: %s%%` rather than the old `Size: %.0f%%`.
- **A `§` colour code stops applying at the next placeholder.** A translated string is split into one part per placeholder, and `TranslatableContents.visit` hands *every* part the component's own style, so formatting opened in one part does not carry into the next. Text that has to keep one colour across a placeholder sets that colour in Java instead — see the two `create.feedback_*` messages in `WaypointCreateScreen`, which apply `ChatFormatting.GRAY` to the whole component so the name and coordinates stay grey.

### Mixins

The mod injects no mixins at all. One mixin config exists and is registered: `easywp.mixins.json` (package `com.easywp.mixin`, common/server, empty), shared via `common/src/main/resources/` and requiring `JAVA_25` compatibility with `requireAnnotations: true` — kept as a wired-up extension point rather than deleted, so adding a common/server mixin needs no new plumbing. There is no client-side config: if client mixins are ever needed, `easywp.client.mixins.json` has to be written and added to both `fabric.mod.json`'s `mixins` array.
