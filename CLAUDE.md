# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**easyWp** — a lightweight Fabric mod for Minecraft that adds persistent, per-world waypoints (create/edit/list, hide/focus, favorites, duplicate into the other half of Overworld↔Nether at 1:8, optional TP for operators, automatic death waypoints, and manual two-way import/export with Xaero's Minimap). Client-side only; the common/server entrypoint does nothing but log. Mod ID: `easywp`. Licensed CC0 1.0.

This file is the sole source of technical documentation for the project: how the mod works today. Planned and in-progress work per release (decisions, delivery plan, per-item status) lives in `Historial de versiones.md` at the repository root, in Spanish; read it before working on a release.

## Repository structure

Multi-module Gradle layout declared in `settings.gradle` (`include 'common', 'versions:26.1', 'versions:26.2', 'versions:26.3'`). Three Minecraft versions are supported — there is no legacy single-module copy and no historical-version scaffolding. Nothing below is written against a fixed count: `checkSharedSources` reads the version list off the included subprojects, so a fourth is `settings.gradle` plus a `versions/<x>/` directory, not an edit to the checks.

- `common/src/main/java/com/easywp/EasyWp.java` — the shared/server `ModInitializer` (just logging). There is no client code in `common/` — the entire client layer (`versions/*/src/client/java/com/easywp/client/`) is intentionally duplicated per version rather than shared. This isn't just a style choice: `common/build.gradle` declares only `fabric-loader` and `slf4j-api` as dependencies, no Minecraft artifact at all, and `common` is its own real Gradle subproject with its own `:common:compileJava` task — so any class in `common/src/main/java` that imports `net.minecraft.*` (client-only or not, e.g. `BlockPos`) would fail to compile standalone, even though it would compile fine once merged into a version's own sourceSet (see below). Pinning `common` to one Minecraft version just to satisfy its own compile would be fragile (it wouldn't actually validate compatibility with the *other* version), and dropping the `java` plugin to stop compiling it standalone is a bigger structural change than the duplication it would save. **Thirty-two of the thirty-three client files are byte-identical across all three versions** (`WaypointStore`, `ImportConfirmScreen`, `Waypoint`, `ModConfig`, `I18nHelper`, `ModernButton`, `WaypointDisplayMode`, `WaypointSortMode`, `WaypointPing`, `ModMenuIntegration`, `UiPalette`, `Icons`, `EasyWpClient`, `WaypointRenderer`, `WaypointCreateScreen`, `DeathWaypointManager`, `ModConfigScreen`, `ModKeyBindings`, `WaypointListScreen`, `DimensionNames`, `XaeroBridge`, `XaeroMinimapBridge`, `XaeroSync`, `XaeroLinkLedger`, `WaypointColors`, `ImportWorldScreen`, `WaypointShare`, `EasyWpCommands`, `ChatAddButtons`, `PlayerPickScreen`, `PopupMenu`, `WelcomeMessage`) — keep them in sync by editing one, diffing, and copying to the *others*, not by trying to relocate them. `.gitattributes` pins the whole tree to LF precisely so that `diff` stays meaningful here.

  The root `checkSharedSources` task enforces this on every `build`, in **both** directions, and across **all** the trees rather than a single pair:
  - a listed file that is not byte-identical in every version fails the build, so a divergence cannot ship. The message names which copies agree with which (`26.1+26.2 vs 26.3`), because with three trees "they differ" no longer says where the edit went missing;
  - a file that is byte-identical in *every* version but *not* listed also fails, with instructions to add it. That second half exists because being identical-but-unlisted is precisely the state in which a later drift goes unnoticed — `ModMenuIntegration.java` sat that way for a while. `intentionallyUnsharedSources` is the escape hatch for a file that matches everywhere only by coincidence; it is empty today.

  Note the asymmetry three trees introduce: a file identical in *some* versions is neither guarded nor flagged. None is in that state today, but a future per-version split of that shape would not belong in `intentionallyUnsharedSources`, which is only for a file that matches in all of them.

  Only one file differs: `ClientCompat.java`, the shim that *exists* to hold the difference (see Entry points below). Its 26.1 and 26.2 copies are identical — those two versions ship as one jar and resolve their renames at runtime (see One jar for 26.1 and 26.2 below) — and the 26.3 copy is its own. Until 1.3.4 four more did — `EasyWpClient` (the render hook), `WaypointRenderer` and `WaypointRenderTypes` (three genuinely different in-world renderers) and `WaypointCreateScreen` (a javadoc paragraph about them). Moving the waypoints to the HUD (see Rendering below) replaced all three renderers with one shared file, deleted `WaypointRenderTypes` and `ShaderDetector` outright, and left the version difference as two accessors in the shim.

  Before `ClientCompat` existed, four more files carried 26.2's renamed vanilla calls inline (`Minecraft.setScreen` → `gui.setScreen`, `Minecraft.gui.setOverlayMessage` → `gui.hud.setOverlayMessage`), which kept them off the guarded list for no better reason than two method names. Route any future rename of that shape through the shim rather than inline, or the file drops out of the shared set and stops being checked. The 26.3 port is what that rule was written for: it renamed a key-constant source, an enum constant and a *type's package*, across four otherwise-shared files, and all of it went through the shim — see Entry points below for what had to change and why a moved type needs a method that hides it rather than one that takes it.
- `common/src/main/java/com/easywp/JsonStore.java` is the exception that proves the rule above: it imports nothing but `java.nio`, so it compiles standalone against this module's Minecraft-free dependency set and every version picks it up from the shared source directory. It is where the durable read/write for both JSON stores lives (see Persistence below). Anything else that is genuinely Minecraft-free belongs here too — as `XaeroWaypointFormat`, `AsyncJsonWriter`, and the three small text helpers added in 1.4.0 do: `DistanceFormat` (the label's `999m`/`1.2km`), `RelativeCoordinate` (vanilla-style `~`/`~5` coordinates) and `NameNumbering` (the lowest free `#N` for a default name) — plus `PairedCoordinates` (the Overworld/Nether 1:8 conversion and the rule that tells a copy across it) and `PendingRemovals` (the per-item countdowns behind the list's undoable delete) — and `WaypointShareFormat` (the chat share line and its parser, see Client commands below) — and `WaypointGroups` (group names, the world's groups, the list filter and hidden groups, see Groups below) — and `WelcomeVersion` (when the welcome message is due, and which release's news it shows).
- `common/src/main/resources/` **does** hold real shared content — non-code resources aren't compiled, so none of the above applies. Every version already merges it in via `resources.srcDirs += project(":common").file("src/main/resources")`. Everything byte-identical between versions lives there: the eight lang JSON files, the mod icon, `textures/waypoint_marker.png`, the 11 icons under `textures/gui/`, and `easywp.mixins.json`. `fabric.mod.json` stays per-version, but its Minecraft range is not written in it: `"minecraft": "${minecraft_range}"` is expanded from each version's `minecraft_version_range` in `gradle.properties` (`~26.1 || ~26.2` for the 26.1+26.2 jar, `~26.3` for 26.3; not `>=26.1 <26.3-`, the form used until 1.4.0-beta.2, which Modrinth's upload could not read to fill in the game versions), so the 26.1 and 26.2 copies are identical and each jar loads only on the versions it was built and checked for. Until then the 26.2 and 26.3 jars declared `>=26.2`/`>=26.3`, which let a jar load on a later version it would crash on. Every asset under `assets/` is shared. (`label_backdrop.png`, a 1x1 white pixel the old 26.2/26.3 world renderers bound as a sampler, was per-version and went with them.)
- `versions/26.1/` — stable branch, Minecraft `26.1.2`, Fabric API `0.155.2+26.1.2`, same HUD renderer as the other two (see Rendering below).
- `versions/26.2/` — Minecraft `26.2`, Fabric API `0.156.0+26.2`. **Not published on its own** (`verification_only=true`): it compiles the same sources against 26.2 so they can be run there with `runClient`, and `checkMergedJar` proves they are the 26.1 jar's (see One jar for 26.1 and 26.2 below); its jars go to `build/verify-libs/`, out of `build/libs/`. 26.2 rewrote world rendering around `SubmitNodeCollector` and moved the HUD-hidden flag from `Options.hideGui` to `Hud.isHidden()`; only the latter still matters to this mod, through `ClientCompat`.
- `versions/26.3/` — Minecraft `26.3`, Fabric API `0.160.5+26.3`, Mod Menu `21.0.0-beta.1` (the only Mod Menu built for 26.3 so far; it is `clientCompileOnly` and never bundled, so a beta costs nothing), Xaero's Minimap `26.5.1` + xaerolib `1.7.8` (26.5.0, which 26.1/26.2 pin, was never published for 26.3). 26.3 replaced the blaze3d pipeline layer with `com.mojang.renderpearl` (moving `RenderPipeline` to another package) and GLFW with SDL, which is why `ClientCompat` grew `blitTinted` and key constants. The camera render state and the Fabric HUD API the renderer uses kept their 26.2 shape.
- Each version subproject compiles `common/` directly into its own jar (`java.srcDirs += project(":common")...` plus `implementation project(":common")`) — `common` is not published as a separate artifact. All three `versions/*/build.gradle` files are byte-identical; everything that varies between them lives in their own `gradle.properties` — including the two things the one-jar setup needs: `minecraft_version_range`, expanded into `fabric.mod.json`, and `verification_only=true` (26.2 only), which sends that subproject's jars to `build/verify-libs/` (see One jar for 26.1 and 26.2). Nothing checks that, the same as before — a new version's `build.gradle` is a `cp` of an existing one, and a difference that creeps in there will not fail a build.
- `common/build.gradle` compiles at **Java 21** while the version subprojects compile at **25**. That is not an oversight: `common` only ever has to satisfy its own standalone `:common:compileJava`, and the sources that actually ship are recompiled at 25 inside each version's `main` sourceSet, which is what `fabric.mod.json`'s `"java": ">=25"` and the mixin config's `JAVA_25` refer to. Keep new `common/` code inside the Java 21 language level or the standalone compile breaks even though the shipped jar would have been fine.

A prior attempt to also support older Minecraft versions (`1.21.1`, `1.21.3`, `1.21.8`, `1.21.11`) was abandoned and removed; see git history if that work is ever resumed.

## Build & run

Requires JDK 25. Gradle Wrapper (Gradle 9.5.1) and Fabric Loom `1.17-SNAPSHOT` are pinned in `gradle/wrapper/` and `gradle.properties`.

```bash
./gradlew build
```

Builds every included subproject and produces the two publishable jars (the last build's copies are also gathered in `latest/` at the repository root by `collectLatestJars`, a `Sync` that every published version's `build` is finalized by, so the folder only ever holds the newest jar of each; it is gitignored):
- `versions/26.1/build/libs/easywp-<mod_version>+26.1-26.2.jar` — for Minecraft 26.1.x **and** 26.2
- `versions/26.3/build/libs/easywp-<mod_version>+26.3.jar`

(plus `versions/26.2/build/verify-libs/`, the same jar built against 26.2 only to be compared — never published).

Other useful tasks:

```bash
./gradlew :versions:26.1:build      # build a single version
./gradlew :versions:26.1:runClient  # launch a dev client for that version (working dir: run/)
./gradlew :versions:26.2:runClient
./gradlew :versions:26.3:build
./gradlew :versions:26.3:runClient
./gradlew clean
```

The mod version is global and set once in root `gradle.properties` (the `mod_version` property); each version subproject appends its own `minecraft_version_suffix` from its own `gradle.properties` to form the jar name. There is no lint task. Correctness is verified via `build`, which compiles every version and runs five checks — `checkSharedSources` (see Repository structure), `checkMergedSources` and `checkMergedJar` (see One jar for 26.1 and 26.2), `checkLangParity`, and `:common:test` — plus manual in-game testing through `runClient` for everything those cannot reach, which is most of the mod. Each can also be run on its own:

```bash
./gradlew checkSharedSources   # every copy of every shared client source still agrees
./gradlew checkMergedSources   # 26.1 and 26.2 have identical client sources and fabric.mod.json
./gradlew checkMergedJar       # ...and building them gives byte-identical classes and resources
./gradlew checkLangParity      # every lang file carries en_us.json's exact key set
./gradlew :common:test         # unit tests of every common/ class
```

`checkLangParity` fails if any lang file is missing a key that `en_us.json` has, if it carries a key `en_us.json` does not (which is a typo'd key nothing will ever look up — the string stays untranslated while the file looks complete), or if one of the six `es_*` copies has drifted from `es_es.json`. The Spanish copies are listed in `spanishCopiesOfEsEs` in the root `build.gradle`; drop a locale from that list the day it earns genuinely regional wording.

### Tests

`common/` is the only module where a test suite can exist at all: every other class needs a running client, while anything living in `common/` (by construction) touches nothing but `java.nio`/plain text. Eleven suites live there today:

- `JsonStoreTest` — `JsonStore` is where a bug costs the most, since the per-world waypoint file is the only copy those waypoints exist in, so the suite pins the guarantees rather than leaving them to be re-derived from the implementation: round-tripping, parent-directory creation, no `.tmp` left behind, no `.bak` on the first write, the `.bak` holding the *replaced* revision on later ones, UTF-8 for non-ASCII waypoint names, a shorter document fully replacing a longer one, and recovery from a truncated target. Checked against two deliberate mutations (skipping the backup snapshot; writing straight to the target instead of via the temp file) and caught both.
- `XaeroWaypointFormatTest` — round-tripping every field, unknown trailing fields preserved instead of dropped, malformed/too-short lines skipped rather than guessed, non-waypoint lines preserved through both `merge` and `removeAll`, `merge`'s add-only idempotency and its guarantee that nothing the caller didn't mention is ever removed, `removeAll` dropping only the waypoints named (a same-named waypoint at another position survives) and matching on name + X + Z *ignoring Y* so the file path agrees with the live bridge, exported waypoints landing in Xaero's own default set, the 21-entry color palette's round-trip, `:` in a name sanitized rather than desyncing the line, non-ASCII names, and the exact `xaero-waypoint:` chat line Xaero's own receiving parser accepts, and `parseChatShareLine` reading that line back (after a sender prefix, with a destination field ignored, a `~` Y as no Y, an out-of-range colour as 0, too few fields or non-numbers rejected) — checked against four more mutations (seven fields accepted; `~` not read; no colour clamp; the tag found only at the start), all caught. Checked against deliberate mutations (`merge` not deduplicating; `merge` dropping what was already in the file; `removeAll` matching on Y as well; `removeAll` dropping non-waypoint lines; the chat line carrying the destination field it must omit) and caught all of them.

- `AsyncJsonWriterTest` — the latest document ends on disk after `flush()`; saves queued while a write is in flight coalesce to the newest (a stalled sink makes the pile-up deterministic); different files are each written, in order; `flush()` waits for the write *in flight*, not just an empty queue; a failed write is reported without dropping the other queued file, and the failed file is retried by its next save; an `Error` thrown by the sink, and a drain the executor refuses to schedule, both leave `flush()` returning instead of waiting forever, with the queue still alive for the next save. Checked against six deliberate mutations (`flush` not waiting; no coalescing; keeping the oldest document instead of the newest; a failure clearing the queue; `drain`'s `finally` not clearing the flag; `write` not clearing it after a refused `execute`) and caught all six.

- `DistanceFormatTest` — metres below 1000, one decimal from 1000 on, truncated like the metres (`1999` → `1.9km`), metres-only ignoring the threshold, a point as decimal separator under German and Spanish default locales, and the cache key changing exactly when the text does across both modes (one key never standing for two texts). Checked against four deliberate mutations (`>` instead of `>=`; rounding instead of truncating; `String.format` without `Locale.ROOT`; a kilometre key that collides with a metres value) and caught all four.
- `RelativeCoordinateTest` — plain numbers, `~` alone, `~5`/`~-3`/`~0.5`/`~+2`/`~.5`, unreadable text (`~~`, `5~`, `~abc`, blank), a space right after `~` rejected as in vanilla, non-finite values (`NaN`, `Infinity`, `1e400`) rejected, and no player (`NaN` base) making every `~` form unreadable while plain numbers still read. Checked against four deliberate mutations (a space after `~` accepted; no finiteness check; the offset ignored; the offset's sign flipped) and caught all four.
- `NameNumberingTest` — 1 on an empty list, continuing after consecutive names, a deleted number handed out again, names of other shapes (`Ping #1`, a lowercase `waypoint #1`, a renamed waypoint) not taking a number, and the count of names not being the number. Checked against two deliberate mutations (starting at 0; count + 1) and caught both.

- `PairedCoordinatesTest` — into the Nether divides by 8 and rounds (`-15` → `-2`, `12` → `2`, `-12` → `-1`), out of it multiplies by 8, a point and its copy are copies in both directions, a copy of a copy is still recognised (`-15` and `-16` both pair with `-2`), and points that do not correspond are not. Checked against three deliberate mutations (flooring instead of rounding; comparing in Overworld coordinates, which misses `-15`'s own copy; ignoring Z) and caught all three.
- `PendingRemovalsTest` — an item expires when its time is up and not a millisecond before, each item runs on its own clock, an undone item never expires, an item stays pending past its deadline until it is taken (so a row cannot flicker back), marking again restarts the countdown, expired items come back in the order they were marked, and `takeAll` ends every countdown. Checked against five deliberate mutations (an off-by-one at expiry; `cancel` keeping the countdown; marking again keeping the old deadline; pending ending at the deadline instead of when taken; `takeAll` leaving them pending) and caught all five.
- `WaypointShareFormatTest` — the three vanilla dimensions written by name and any other by full id, the name keeping its case, a round trip for every kind of dimension, a name containing `>>>`, spaces and accents (and one that looks like a whole line) still read as the name, 1.3.x lines read (a prettified modded dimension coming back as `null`), vanilla names in any case, extra whitespace tolerated, and everything that is not a share line rejected (no separator, two coordinates, no dimension, no name, a decimal, trailing text, past `int` range). Checked against six deliberate mutations (a lazy name group, which splits at the first `>>>`; a modded dimension written without its namespace; vanilla names compared case-sensitively; the name upper-cased as in 1.3.x; the out-of-range catch removed; any text accepted as a dimension id) and caught all six. `findIn` (the line inside a received message) is pinned for vanilla's `<Steve> ` and whisper prefixes, `[A -> B] `, `» `, a plugin prefix with several parts ending at the last one, a `>>>` inside the name not taken for a prefix, a bare line, and ordinary messages yielding nothing; checked against three more mutations (the first prefix end instead of the last; no skip of a `>>>` in the name; the prefix never stripped), all caught. `chatSafe` (what a player's chat may carry: no section sign, DEL or control character, accents and emoji kept) and `fitLine` (the name cut, never the rest of the line, until it fits; never splitting a character; `null` when nothing fits) are pinned too, and checked against four mutations (no section-sign filter; control characters kept; a cut splitting a surrogate pair; no cut at all), all caught.

- `WaypointGroupsTest` — names trimmed, whitespace collapsed and cut at 16, a typed name reusing an existing group that differs only in case, the world's groups as a sorted union, the filter keeping all / no group / one group, one hidden group being enough to hide, hidden groups pruned to those that exist, the per-waypoint limit and duplicate check, and suggestions matching the typed text while skipping assigned groups. Checked against seven deliberate mutations (no whitespace collapse; a case-sensitive resolve; "no group" keeping everything; only the first group checked for hidden; an off-by-one on the limit; assigned groups still suggested; pruning keeping everything) and caught all seven.
- `WelcomeVersionTest` — due when never shown or shown for another version (every alpha and beta counts), not due for the same one or with no version known, and a version's release found by cutting at the first `-` or `+`. Checked against four deliberate mutations (due only when never shown; due with no version; the build part kept; the pre-release part kept) and caught all four.

JUnit 5 is pinned by `junit_version` in the root `gradle.properties`. Anything added to either suite should be held to the same bar: checked against a real, deliberate break in the implementation, not just passing against the current one.

### CI

`.github/workflows/build.yml` runs `./gradlew build` on every push and pull request (Ubuntu, Microsoft JDK 25) and uploads the resulting jars. There is no separate test job: `build` already runs `:common:test`, `checkSharedSources`, `checkMergedSources`, `checkMergedJar` and `checkLangParity`, so the one command is the whole gate. The artifact path is `versions/*/build/libs/*.jar` — which holds exactly the two publishable jars, since the 26.2 verification build goes to `build/verify-libs/` — not `build/libs/`: the root project has no `java` plugin at all, so nothing is ever produced there, and the workflow used to upload an empty artifact because of it.

`runClient` writes its sandbox to the invoking subproject's own `run/` — `versions/26.2/run/config/easywp/` holds a real `config.json` and a `waypoints_sp_New_World.json`, useful as live examples of both file formats. The `run/` at the repository root is a leftover from the abandoned single-module layout. All of it is gitignored (`run/`, and now `logs/` as well, after an empty `versions/26.2/logs/latest.log` was committed once by accident); none of it is mod source.

## Architecture

### Entry points (`fabric.mod.json`, per version)

- `com.easywp.EasyWp` (in `common/`) — `ModInitializer`, server/common side, effectively a no-op (just logs startup).
- `com.easywp.client.EasyWpClient` (shared) — `ClientModInitializer`, and the whole of the client wiring: `ModKeyBindings.register()`, `EasyWpCommands.register()` (the `/easywp` client command, see Client commands), `ChatAddButtons.register()` (the chat `[+]`, see Sharing), `WelcomeMessage.register()` (see Welcome message), the two HUD elements that draw the waypoints (`HudElementRegistry.attachElementBefore` `MISC_OVERLAYS` and `SLEEP` — see Rendering for why two), and two `ClientTickEvents.END_CLIENT_TICK` handlers: `DeathWaypointManager`, and `WaypointStore.forgetWorld()` while there is no level or `WaypointStore.tickPendingRemovals()` while there is one (see Persistence). `WaypointRenderer` itself has no init step: its state is all static field initializers with no side effects.
- `com.easywp.client.ClientCompat` (one copy for 26.1+26.2, one for 26.3; not an entrypoint) — the shim holding every vanilla name that changed between versions without its meaning changing. It is the one client file that is *supposed* to differ between jars, and it exists so the screens and managers that would otherwise carry those renames inline can stay byte-identical and therefore guarded by `checkSharedSources`. Add to it only for renames of this shape — same semantics, different vanilla name. Where the versions genuinely do different work the difference belongs in the caller, where it can be explained. It now holds:
  - `setScreen` and `setOverlayMessage` — `setScreen` is `Minecraft.setScreen` on 26.1 and `Gui.setScreen` from 26.2. **Not** `Minecraft.setScreenAndShow`, which all three have: it sets the screen and then calls `renderFrame(false)` on the spot, a frame that does not advance game time, rendered from inside the click that changed the screen. The shim used it until 1.4.0-beta.2, and it showed as a flicker on every screen change (most visibly saving the form back to the list, and every Reset in the settings). The overlay message moved from `gui` to `gui.hud` in 26.2. Unchanged again in 26.3.
  - `KEYBOARD` and the seven `KEY_*` ints — 26.3 replaced GLFW with SDL. `org.lwjgl.glfw.GLFW` is simply not on the 26.3 classpath, its key codes moved onto `InputConstants` itself (`InputConstants.KEY_K`, and SDL's own `KEY_RETURN`/`KEY_NUMPADENTER` for the two Enters), and `InputConstants.Type.KEYSYM` — GLFW's name for a layout-mapped key — became `Type.KEYBOARD`. `ModKeyBindings` and `WaypointCreateScreen` name the constants here instead, and stay shared.
  - `MOUSE_LEFT` — SDL renumbered the mouse buttons too: left is `1` in 26.3 (`InputConstants.MOUSE_BUTTON_LEFT`), `0` under GLFW. Every click this mod handles by hand (`PopupMenu`, the list's double-click copy) compares `MouseButtonEvent.button()` against this, never a literal: the literal `0` made all of them dead on 26.3 until alpha.6. Like the `KEY_*` ints it is a compile-time constant, so each jar carries its own value.
  - `addChatMessage` — a local chat line (the chat `[+]`): `gui.getChat()` on 26.1, `gui.hud.getChat()` from 26.2, the same move as the overlay message.
  - `isHudHidden` and `cameraRenderState` — what the HUD renderer needs from the frame. F1 is `Options.hideGui` on 26.1 and `Hud.isHidden()` from 26.2; the frame's `CameraRenderState` is reached through `GameRenderer.getGameRenderState()` on 26.1 and `gameRenderState()` from 26.2.
  - `blitTinted` — the one that is *not* shaped like the others, and the reason worth reading. 26.3 moved `RenderPipeline` from `com.mojang.blaze3d.pipeline` to `com.mojang.renderpearl.api.pipeline`. A moved **type** cannot hide behind a method that takes it as a parameter, which is what `Icons.drawMarkerIcon(g, pipeline, ...)` and the two screens' `RenderPipeline pipeline = RenderPipelines.GUI_TEXTURED;` were doing — four shared files naming the type in their own signatures. So the shim takes the *texture* and looks the pipeline up itself. Every call site passed `GUI_TEXTURED` anyway, so nothing was lost by not letting them choose, and `Icons`, `WaypointListScreen` and `WaypointCreateScreen` stopped naming the type at all. The general rule: when a rename moves a type rather than a method, the shim has to swallow the type, not accept it.
- `com.easywp.client.ModMenuIntegration` (shared) — optional `modmenu` entrypoint returning `ModConfigScreen`. Fabric only instantiates it when Mod Menu is installed, and Mod Menu is a `clientCompileOnly` dependency (`18.0.0` for 26.1, `20.0.1` for 26.2, `21.0.0-beta.1` for 26.3, from the Terraformers maven), so it is never bundled. Note that Loom 1.17 exposes no `mod*` configurations at all — this project declares even Fabric API through plain `implementation`, and remapping happens anyway.
- `com.easywp.client.XaeroBridge` (shared, not an entrypoint) — the second optional `clientCompileOnly` dependency, same shape as Mod Menu but gated explicitly rather than by Fabric's own conditional-instantiation trick: `xaero.minimap:xaerominimap-fabric-<minecraft_version>` (`26.5.0` for 26.1/26.2, `26.5.1` for 26.3, pinned per version in `gradle.properties`, plus `xaero.lib:xaerolib-fabric-<minecraft_version>` — `1.7.3`, and `1.7.8` for 26.3 — pinned explicitly rather than left to the POM's version range), from `https://chocolateminecraft.com/maven`, added to every `versions/*/build.gradle` by hand — those files are byte-identical and nothing checks that, the same as every other line in them. See Xaero's Minimap integration below for why the gate is two separate questions (`isModInstalled()` vs. `isAvailable()`) plus a `LinkageError` catch rather than Mod Menu's simpler pattern, and why `XaeroMinimapBridge` is the one other file (besides `ClientCompat`) allowed to import from outside `net.minecraft.*`/this mod's own packages.

`environment` is `client`: the common entrypoint only logs, and nothing in the mod needs to run server-side.

### One jar for 26.1 and 26.2

26.1 and 26.2 ship as a single jar, `+26.1-26.2`, built by the 26.1 subproject against the oldest of the two. It was possible because compiling the shared sources against each gave byte-identical classes except `ClientCompat`: everything else names only members both versions have with the same signature. What the two still differ in is five renames, all from 26.2 moving the HUD out of `Gui` into a public `Gui.hud` field, moving the screen into `Gui`, and renaming one accessor:
- `Minecraft.setScreen` → `Gui.setScreen`,
- the overlay message and the chat (`gui.setOverlayMessage`/`gui.getChat` → `gui.hud.…`),
- F1 (`Options.hideGui` → `Hud.isHidden()`),
- `GameRenderer.getGameRenderState()` → `gameRenderState()`.

`ClientCompat` resolves them once, by name, in its static initializer, with `MethodHandles.publicLookup()`: whether `Gui` has the `hud` field decides the overlay, the chat and F1, `setScreen` is whichever of `Minecraft` and `Gui` has it, and the accessor is whichever of the two names exists. The handles are `static final`, so the JIT folds them into direct calls — the two read every frame cost what the plain calls did. A version where a name does not resolve fails at startup with a clear exception rather than on first use, and `fabric.mod.json`'s `~26.1 || ~26.2` keeps the jar off any version that was not checked.

The 26.2 subproject stays, marked `verification_only=true` in its `gradle.properties`: it compiles the very same sources against 26.2 (its `ClientCompat` is a copy of 26.1's), so `runClient` there runs exactly what ships, and its jar goes to `build/verify-libs/`. Two root checks, listed by `mergedVersions` in `build.gradle` (the first one's jar is published), keep that true:
- `checkMergedSources` — every client source, `ClientCompat` included, and `fabric.mod.json` byte-identical across the group. A rename between these versions goes into `ClientCompat` as a lookup, never into a per-version copy.
- `checkMergedJar` — the two jars hold byte-identical classes and resources (only the manifest, which records the Minecraft each was built against, may differ). Same bytecode from two Minecrafts is the proof that every name the jar uses exists in both. Both checks were run against a deliberate one-line difference in the 26.2 copy and failed as they should.

Mod Menu and Xaero's Minimap are covered the same way: the 26.2 subproject compiles against their 26.2 builds, so `ModMenuIntegration` and `XaeroMinimapBridge` coming out identical is the proof that the published jar links against those too.

What it does not change: each version still has to be tested in the game — one jar, two Minecrafts — and the test is best done with the published jar itself in a real 26.1 and a real 26.2 instance, since `runClient` on 26.2 runs the verification build (identical classes, but not the file that is uploaded). 26.3 stays separate: it moved `RenderPipeline` to another package and replaced GLFW with SDL, and a moved *type* sits in the signatures of every class that touches it, which a by-name lookup cannot hide.

### Keybindings & input

`ModKeyBindings` registers five keys under one custom `KeyMapping.Category` (`easywp:easywp_controls`, named by the `key.category.easywp.easywp_controls` lang key) and then drives all of them from a single `ClientTickEvents.END_CLIENT_TICK` handler using `while (key.consumeClick())`:

| Key | Default | Action |
| --- | --- | --- |
| `key.easywp.toggle` | `K` | Cycles `WaypointDisplayMode` (world markers ⇄ disabled) and shows the new state as an overlay message |
| `key.easywp.create` | `N` | Opens `WaypointCreateScreen` pre-filled with the player's own block position |
| `key.easywp.list` | `J` | Opens `WaypointListScreen` |
| `key.easywp.ping` | `H` | Opens `WaypointCreateScreen` pre-filled with `WaypointPing.target(client)`, the crosshair raycast. Was `V` until Fast Ping (below) took it over. |
| `key.easywp.fast_ping` | `V` | Creates a waypoint at the crosshair raycast directly, with no screen - the form's own default-name and restore-visibility logic duplicated inline since there is no `WaypointCreateScreen` instance to call into. Replaces what used to be a no-menu *quick-create* bound to `G` and targeting the player's own feet; Fast Ping keeps the no-menu part but targets the same ray as classic Ping above, sharing its `ModConfig.Ping` settings (range, fluids, follow-render-distance) rather than growing a second copy of them. Named `easywp.create.ping_name` ("Ping #N"), colored with `WaypointColors.random()`, and flagged `Waypoint.fastPing` so `ModKeyBindings.nextFreeFastPingNumber()` can number the next one as the lowest number no existing Fast Ping uses. Deleting pings frees their numbers, so after clearing old pings numbering restarts at #1, and a name still in use is never repeated. (A plain count, the first version, repeated "Ping #3" once #1 was deleted from #1-#3. "Highest + 1", the second, kept climbing past numbers the player had already freed.) The number is the name's last digit run, read only from waypoints still flagged `fastPing`, so it works in any locale and never picks up a waypoint the player renamed by hand. Not `B`: that's Xaero's Minimap's own default "new waypoint" key, and the two would otherwise fire on the same press. |

Rebinding happens in Minecraft's own Controls screen — `ModConfigScreen` deliberately does not duplicate it. One non-obvious detail lives in that same tick handler: the "remember visibility across restarts" setting is applied on the **first tick**, not in `onInitializeClient()`, because `ModConfig.get()` needs `Minecraft.getInstance().gameDirectory`, which is not guaranteed ready during client init. A one-shot `appliedRememberedVisibility` flag guards it.

### Client commands

`EasyWpCommands` registers one client command, `/easywp`, through Fabric's `ClientCommandRegistrationCallback` (`fabric-command-api-v2`, part of the Fabric API the project already depends on; its builder class is `ClientCommands` in all three versions — the `ClientCommandManager` of older Fabric APIs no longer exists). Client commands run entirely on this side, so they work on any server. Subcommands: `list` (the current dimension's waypoints, nearest first, with distance in `DistanceFormat` and clickable `[Focus]` and — with permission — `[TP]`), `add <name> [x y z] [color]`, `remove`, `focus`, `share`, `tp <name>`, and `open <dimension> <x> <y> <z> <name>` (the create screen pre-filled, for the chat `[+]` of 1.4.0's alpha 5); `/easywp` alone prints a one-line help.

- **Clicks run without a confirmation.** Fabric injects at the head of both `ClientPacketListener.sendCommand` and `sendUnattendedCommand` (the chat click path, confirmed from the jars of all three versions), so a clicked `/easywp ...` runs before vanilla's `verifyCommand` can ask. A clicked vanilla `/execute ... tp` would ask (`PERMISSIONS_REQUIRED`), which is why `list`'s TP click runs `/easywp tp` instead of the teleport itself. `/easywp tp` then sends the vanilla command with `sendCommand`; Fabric's dispatcher does not know `execute`, ignores it, and vanilla sends it to the server.
- **Names.** A name at the end of a command is the rest of the line (`greedyString`), so spaces need no quotes; surrounding quotes are stripped if typed anyway. `add`'s name has arguments after it, so it is a quoted string or one token. Brigadier's own unquoted strings accept only `[0-9A-Za-z_.+-]` — no accents, no `~` — so names, coordinates and colours are read by three small custom `ArgumentType`s that take everything up to the next space. Nothing needs registering for them: a client dispatcher is never serialised. `add` refuses a name over 32 characters (`MAX_NAME_LENGTH`, vanilla `EditBox`'s default, which the create screen's name field keeps) or wider than the list shows whole (`WaypointListScreen.NAME_FIT_WIDTH`, see UI); `open` truncates to both.
- **Which waypoint a name means.** Exact match first, else case-insensitive; never one pending deletion. With several, the nearest in the player's dimension (else the first in another), and the player is told how many share the name. `list`'s clicks name their waypoint the same way, so with duplicate names a click acts on the nearest. Suggestions offer every name in the world.
- **`add`'s colour and coordinates.** Coordinates go through `RelativeCoordinate` (`~`, `~5`), a colour is `#RRGGBB` or `RRGGBB`, and without one it is `WaypointColors.random()` like Fast Ping. The colour branch is registered *before* the coordinate branch on purpose: Brigadier keeps the first of two branches that both consume the whole input, so `add Base 123456` is a colour rather than an incomplete X. `add` turns the waypoints back on if they were off (`ModKeyBindings.showWaypointsAfterCreate`, shared with the form and Fast Ping).
- **`remove` is final**, with no undo: there is no row to offer one from. **`focus` always focuses** (`WaypointStore.focus`, shared with the list's swatch); it does not toggle.
- **`open`** resolves the dimension through `WaypointShareFormat.dimensionFromLabel` and keeps it only if the server has that level (`ClientPacketListener.levels()`); anything else becomes the player's own. The screen (`WaypointCreateScreen(pos, dimension, name)`, which saves into that dimension) is opened on the next client tick: the chat closes itself right after running a typed command, and would close a screen opened from inside it.

**The share line is `WaypointShareFormat` (in `common/`)**: `NAME >>> DIMENSION X Y Z`, the name as written, `Overworld`/`Nether`/`The End` by name and any other dimension by its full id. It is fixed in code rather than in the lang files (where `easywp.share.chat` used to be) because it is read back, and a translation could break the parser. `parse` reads from the right — the last three integers, then the last `>>>` before them — so a name may contain `>>>` and a dimension may contain spaces; 1.3.x lines (upper-cased name, prettified modded dimension) still parse, the unresolvable dimension coming back as `null`. The whole line must be a share line; finding one inside a longer message is for the chat `[+]`.

### Sharing

Everything that turns a waypoint into text or back goes through `WaypointShare` (client) on top of `WaypointShareFormat` and `XaeroWaypointFormat` (common): `chatLine` (the share line, or Xaero's with `xaeroChatFormat` on — always one the server accepts: the name goes through `WaypointShareFormat.chatSafe` and is cut by `fitLine` to `CHAT_MAX_LENGTH` (256, less `msg <player> ` for a private one), since vanilla disconnects a player whose chat carries a section sign or runs past 256, and an imported name can do either), `plainLine` (always the share line), `send`/`sendPrivate`/`copy`, `exportLines`, and `parseLines` for pasted text.

- **Sharing from the list is in the row's "More options" menu**, after favorite and duplicate (`addShareItems`); the row's own share button was removed in 1.4.0's alpha 5. "Share in chat" sends and closes the list, as the button used to. "Send privately..." appears only when `WaypointShare.otherPlayers` (the tab list minus the player and any blank or spaced name, which server plugins use for fake decoration entries no `/msg` reaches) is non-empty — so never in singleplayer — and opens `PlayerPickScreen` (vanilla-styled, a search box with the focus, one button per player, scrollable); picking one sends vanilla's `/msg <player> <line>` (respecting `xaeroChatFormat` like the public share) and closes to wherever the list closes to. "Copy to clipboard" copies the plain share line whatever the chat setting, and keeps the list open.
- **Clipboard export and import.** A button beside the gear (bottom-left, screen-anchored, a hand-drawn "copy" glyph) copies what the list shows — this tab narrowed by the search, without pending deletions — one share line each. Ctrl+V in the list (`KeyEvent.isPaste()`, only while no `EditBox` has the focus, so in the search box it pastes there) parses the clipboard: share lines found with `findIn` (so a line copied out of chat with its sender still reads) and `xaero-waypoint:` lines, everything else skipped. A share line carries no colour, so it gets `WaypointColors.random()`; a Xaero line its palette colour. An unnamed or unknown dimension, and a Xaero line's missing Y, become the player's own (not the tab's). The result is previewed by `ImportConfirmScreen`'s second constructor and merged with `mergeFrom`, additive and deduplicated as a world import.
- **The chat `[+]` (`ChatAddButtons`).** Listens to `ClientReceiveMessageEvents.CHAT` and `GAME` (`/msg` and chat plugins arrive as system messages). On `CHAT` the player's own text (`PlayerChatMessage.signedContent()`) is parsed first, which reads a name containing `: ` whole; otherwise `findIn` on the displayed text, which takes the text after the *last* `": "`/`"> "`/`"] "`/`"» "` before the separator — the last because plugin prefixes stack (`[Admin] Steve: `), at the cost of a name containing one of those losing its first part on that path. An `xaero-waypoint:` line gets a `[+]` only when Xaero's Minimap is not installed (it offers its own `[Add]` otherwise). Own messages are skipped: the sender's id on `CHAT`, and any line `WaypointShare` sent in the last 30 s (which also covers vanilla's "You whisper to Bob" echo). The `[+]` line (`chat.add_button` + `chat.add_text`, hover with dimension and coordinates) runs `/easywp open <dim> <x> <y> <z> <name>` — the dimension resolved against the server's levels on receipt, a Xaero line's missing Y sent as `~` — and is added through `ClientCompat.addChatMessage` on the next tick, since the event fires before vanilla adds the message it belongs to.

### Groups

A waypoint can be in several groups (`Waypoint.groups`, a list of names, never null). Groups are labels, not stored on their own: the groups a world has are the union of its waypoints' groups (`WaypointStore.allGroups()`, sorted ignoring case), so a group whose last waypoint goes simply stops existing, with no management screen. Waypoints pending deletion still count, so undoing the deletion of a group's last waypoint brings the group back as it was. The rules live in `WaypointGroups` (in `common/`, with tests): names are trimmed, whitespace-collapsed and at most 16 characters (`MAX_NAME_LENGTH`), a waypoint takes at most 4 (`MAX_PER_WAYPOINT`) — together what fits as two rows of chips — and names compare exactly except where the player types one, where `resolve` reuses an existing group that differs only in case.

- **Saving.** `waypoints_*.json` gets an optional `groups` array, written only when the waypoint has any (null otherwise, which Gson skips), so a waypoint in no group saves exactly as before and older versions ignore the key. Loading cleans it the way the form would (blank or duplicate names dropped). `mergeFrom` keeps a waypoint's groups; whether one is hidden is the importing world's own choice. The split of old shared waypoints copies them too. Nothing else carries groups: not the share line (F7), Xaero's sets, `/easywp add`, Fast Ping, death waypoints, or the form's "Save and duplicate" copy (which takes only name and colour).
- **Assigning (`WaypointCreateScreen`'s "More options" page).** One chip per assigned group, in up to two rows, removes it on click; below the chips a field (`groupField`, created once with the others) plus "+" adds a group. The chips sit above the field so the menu that opens under it never covers them, and that menu shows at most 3 rows so it ends inside the modal. While the field has the focus a `PopupMenu` under it offers the world's groups matching the text that the waypoint does not have yet, led by "Create group ..." when the text names a new one, or says the waypoint is full. Chips are rebuilt on their own (`refreshGroupChips`), not through `rebuildWidgets`, which would clear the focus and close the menu between two additions. Enter in a non-empty group field adds the group instead of saving the form, and a name still typed in the field when the form is saved is added rather than lost (`groupsToSave`).
- **Filtering (`WaypointListScreen`).** The header row is search box, group filter, the selected group's eye and the sort button; with no single group selected the filter takes the eye's slot, so the search box and the sort button never move. The filter opens a `PopupMenu` (All, No group, every group, a hidden one marked " (hidden)", a tick on the current choice, scrolling past 8). It applies within the dimension tab, before the search. It is not saved — the list opens on All — and drops back to All when its group stops existing.
- **Hiding.** The eye beside a selected group hides or shows the whole group (`WaypointStore.setGroupHidden`), in the world too: `Waypoint.isShown` is false for a waypoint with **any** hidden group, unless it is the focused one, which stays drawn. The list dims those rows and closes their eyes like any hidden waypoint. A waypoint's own eye still toggles its own `visible`, which does not override its group. `isInHiddenGroup` returns at once while nothing is hidden, since the renderer asks it for every waypoint every frame.

`PopupMenu` (shared, client) is the hand-drawn menu all three of these use, along with the list's row "More options": the owner builds it each frame from its own state, places it inside the modal (`placeAt` pulls it back in), draws it last in its own stratum and hands it clicks and wheel turns first; the owner keeps the scroll offset, since the menu does not survive a frame.

### Welcome message

`WelcomeMessage` (shared) writes a few local chat lines the first time a world is entered after installing or updating, and only these: a title with the version, the key that leads to the settings (the list's gear, named with the list key's binding as it is **now** — `KeyMapping.getTranslatedKeyMessage()`, since the player may have rebound it — plus "or Mod Menu" only when Mod Menu is loaded), and the release's news. An earlier build also listed all five keys; it was cut to keep the message to what is new. It waits 40 ticks after the player and level appear, so it lands after what a server prints on join, and is checked once per world entry.

Whether it is due is `WelcomeVersion.isNew(onboarding.lastSeenVersion, version)`: the full version from `FabricLoader`'s metadata, so every alpha and beta shows it once, and 1.3.x players see it once on updating (their config has no `onboarding` group). The version is written back before the lines are sent. The news are lang keys `easywp.welcome.news.<release>.N`, with `<release>` from `WelcomeVersion.release` (`1.4.0-alpha.7` → `1.4.0`), read from 1 until the first missing one with `Language.has` — so a release adds its lines to the lang files and nothing else, and one without any just leaves the news out.

**The welcome text is approved by the user, per version, before it ships.** Whenever a version's welcome lines are written or changed (`easywp.welcome.*` in `en_us.json` and `es_es.json`), show the user the full message as it will appear in the chat — title, settings line and every news line, in English and Spanish — as a plain text block in the conversation, and wait for their approval or edits before committing. Do not treat lang-file wording for this message as an implementation detail.

### Data model

`Waypoint` is a POJO: `name`, `pos` (`BlockPos`), `color` (ARGB int), `dimension`, `visible`, `focused`, `forceVisible`, `death` (marks an automatic death waypoint), `fastPing` (marks one Fast Ping created, see Keybindings above), `favorite` (since 1.4.0: first in the list, a star before the name, and its own fade when not looked at), `createdAtMillis` (stamped with the current time by every constructor short of the full eight-argument one, since those are only ever used to create a new waypoint — the create screen, Fast Ping, a Xaero import, a duplicate; the full one is for rebuilding from a save or copying from another world, which keep the original. Waypoints created before 1.4.0 carry 0: their real time was never recorded and cannot be recovered). It also carries a small render-side label cache (`cachedLabelText`/`cachedLabelWidth` plus the inputs they were built from, checked via `labelCacheMatches()`/written via `setCachedLabel()`) — riding on the waypoint itself rather than a separate map, since nothing else in the mod uses a store abstraction either, and it needs no cleanup when a waypoint is deleted (see Rendering below). The live list for the current world is held in-memory as a static `List<Waypoint>` on `WaypointStore`, read/written directly by the UI screens and the renderer — there is no further state/store abstraction. `WaypointStore` (split out of `WaypointRenderer` in 1.3.4, which used to do both) owns the list, the world identity, loading, saving and the cross-world import helpers; `WaypointRenderer` only draws.

**A waypoint belongs to exactly one dimension.** `positionIn(dimension)` is its position there, `null` anywhere else; `dimensionOrOverworld()` stands in for a missing dimension from old saves, and the vanilla dimension ids are the `DimensionNames.OVERWORLD`/`NETHER`/`END` constants rather than literals. Until 1.4.0 a `shared` waypoint was also drawn, converted 1:8, in the other half of the Overworld/Nether pair (a portal toggle in the form and in each list row); that mirroring was removed in 1.4.0 and replaced by an independent copy — the create screen's "Save and duplicate", and `WaypointStore`'s split of old shared waypoints on load (see Persistence). `pairedDimension()` (the other half of the pair, or `null`) and `convertedPosition()` (the 1:8 position there: X/Z divided by 8 into the Nether, multiplied out of it, rounded, Y unchanged) are the one definition of that conversion, used by both, built on `PairedCoordinates` (in `common/`). A name left out of a hand-edited file loads as `Waypoint`, since everything that shows or matches a name expects one. A waypoint also carries a never-saved `pendingRemoval` flag: deleted from the list and still within its undo (see Persistence); `isShown` is false for it.

**Whether a waypoint is drawn is defined once too:** `isShown(anyFocused)` = `visible && (!anyFocused || focused || forceVisible) && (focused || not in a hidden group)` (see Groups below), with `anyFocused` from `WaypointStore.hasAnyFocused()` — any focused waypoint of the world, *in any dimension and whatever the list's search shows*. The renderer draws by it, and `WaypointListScreen` dims rows and picks the eye icon by it, so the list always shows what the world shows. The two used to be separate copies that disagreed: with a focus active the icon checked only `focused || forceVisible` (a hidden focused waypoint kept an open eye), and the list counted the focus only among the rows it was showing, so a focus in another dimension, or filtered out by the search, left rows looking visible that the world was hiding. `forceVisible`, `fastPing` and `favorite` are setter-only (not in the canonical constructor): each is set on a plain `Waypoint` after it is built — `fastPing` by Fast Ping, `forceVisible` by the list's eye button, `favorite` by the create screen, all three by loading — so adding either to the constructor would mean touching call sites that never need it. Unfocusing (clicking the focused swatch again) clears `forceVisible` on **every** waypoint, not just the one that was focused; it used to clear only that one's and leave the rest for the next focus to clear, invisible while nothing is focused but stale once the flag started being saved. `WaypointCreateScreen.saveWaypoint()` clears `fastPing` the moment a Fast Ping is edited, the same way it already clears `death` - once reshaped by hand it's a permanent waypoint the player meant to keep, not a throwaway ping, and it stops counting toward the next one's `Ping #N` number. Two more flags have come and gone, and a `waypoints_*.json` written while either existed still carries them — which Gson simply ignores, so there is nothing to migrate: `portal` marked a waypoint the automatic portal-crossing feature created (removed along with that feature), and `fromXaero` marked one an automatic Xaero import had created so deleting it locally also deleted it from Xaero (removed along with the automatic sync — see Xaero's Minimap integration below for what replaced it).

### Persistence

Four separate JSON stores, all under `<game_dir>/config/easywp/`:
- **Per world/server**: `waypoints_<worldId>.json` (`worldId` = `sp_<sanitized_world_name>`, `mp_realm_<sanitized_realm_name>`, `mp_<sanitized_ip>`, or `mp_lan`).

  **A Realm is filed under its name, a direct server under its address, and that distinction is load-bearing.** `ServerData.ip` is the only address the client has, and for a direct server it is a stable identity. For a Realm it is not: it is the session address Mojang's backend resolves per join attempt (`RealmsJoinInformation.address()`, region-routed via `RegionData`), which `RealmsServer.toServerData(String)` drops straight into that same `ip` field — confirmed from the client jar's own bytecode. It changes on its own, with nothing the player did: a Realm that was updated between two sessions came back on a different address, which produced a different `worldId`, which loaded an empty file, and the waypoints looked deleted while the real file sat intact under the previous address. `ServerData.Type.REALM` is what separates the two cases, read via `ServerData.isRealm()` (vanilla's own one-line `type == Type.REALM`, so no extra import and no assumption about the accessor's name). That the branch fires at all is confirmed the same way: `RealmsConnect$1` builds `server.toServerData(host + ":" + port)` and hands it to `ClientHandshakePacketListenerImpl`, which is what becomes `Minecraft.getCurrentServer()`.

  **The name is the best identity reachable from here, not a perfect one, and the difference is worth stating.** `RealmsServer` carries a genuinely stable `long id`, but `toServerData` does not pass it on and `ServerData` is all `getWorldId()` ever sees, so the name is what is left. It only changes when the owner renames the Realm — rare, deliberate, and fixable by renaming the file to match, which a per-join address is not. It notably does **not** change when the Realm switches to a minigame: that is `RealmsServer.minigameName`, a separate field, and `RealmsConnect` sets it on the packet listener rather than on this `ServerData`.

  `RealmsServer.parse` builds `name` fresh from the Realms API's JSON on every fetch (confirmed from bytecode: a straight `GuardedSerializer.fromJson` with no cache layer in front of it), so short of an actual rename this value is exactly as stable as it looks — there is no staleness path where the same Realm hands back a different name across two sessions.

  Three limits come with that, one handled and two accepted — all three are the same root cause (two different Realms landing on the same *file* name), not three unrelated bugs, and all three needed something more specific than "same name" to see:
  - **`ServerData.name` is never null on a Realm, so a null-check is the wrong guard.** `toServerData` is `new ServerData(Objects.requireNonNullElse(this.name, "unknown server"), address, REALM)` — vanilla has already substituted a *constant* literal. Letting it through would file every unnamed Realm into one shared `waypoints_mp_realm_unknown_server.json`, showing each other's waypoints. `realmFileName()` rejects that literal (and a blank name) and falls back to the address instead: mixing two Realms' lists together is worse than the instability this branch exists to fix, which only makes waypoints look missing while the real file stays intact and recoverable. This one is handled.
  - **Two Realms with the identical raw name collide**, and nothing in `ServerData` can disambiguate them — `RealmsServer` carries a real `long id`, but it never reaches `ServerData`. Accepted: the fix is renaming one of them, and this is a real regression against the old address scheme, which never collided this way (it collided a different way instead, by changing under a single Realm — see above).
  - **Two Realms with *different* raw names can still collide, because sanitizing or filesystem case-folding can make them equal.** `UNSAFE_FILENAME_CHARS` maps `"My Realm"` and `"My:Realm"` to the same `My_Realm`; independently, Windows and default macOS resolve file names case-insensitively, so `"MyRealm"` and `"myrealm"` address one file on this project's own dev machine even though the sanitized strings differ. Neither collision needs a rename, and neither is exotic enough to dismiss. Accepted for the same reason as the identical-name case — nothing past the name is available to disambiguate with, and the fix is the same: rename one Realm.

  `getWorldId()` lives in `WaypointStore`, a shared source, so `checkSharedSources` keeps its three copies identical.

  Orphaned files from before that fix are left alone on purpose. A player who used a Realm under an older build has their waypoints in a `waypoints_mp_<old-address>.json` nothing will open again, and *which* file that is cannot be decided from here: a session address is opaque and carries nothing tying it back to a Realm, so an automatic rename could just as easily adopt some unrelated server's list. `loadFromFile` instead logs one INFO line the first time a Realm comes up empty, naming the `waypoints_mp_*.json` files present and the name to rename one to. That is the whole migration: a pointer, never a move.

  **The manual cross-world import (`ImportWorldScreen`, reached from the full-width button at the top of `ModConfigScreen`) is what a player does with that pointer**, and it exists for exactly this case - a Realm's own file address-hopping and stranding waypoints under an old name - though nothing about it is Realm-specific: it lists every `waypoints_*.json` under the config directory except the current world's own (`WaypointStore.listOtherWorldFiles()`), one full-width row per file naming the world/server (`prettyWorldName()`, the lossy inverse of `getWorldId()`'s four prefixes - `sp_`/`mp_realm_`/`mp_`/`mp_lan` - good enough for display, never used for anything else) and how many waypoints it holds (`countWaypointsIn()`, read the first time a row is shown and kept per file for as long as the picker is open — counting flushes pending saves and parses the whole file, and the rows are rebuilt on every scroll step; none of these files can change meanwhile, since the only file an import writes is the current world's own, which is never listed). Clicking a row opens `ImportConfirmScreen`, which asks "are you sure you want to import the waypoints of WORLD?" (`easywp.import.confirm_message`) above a preview of the file's waypoints (name + coordinates, at most 7, then a `...` line) and imports only on confirm. The list it previews is the same one it merges, read once, so the two cannot disagree. Either answer returns to the picker, so a second file can be imported in the same visit. Both screens are deliberately vanilla-styled (default background, white title, vanilla `Button`s), not this mod's dark modal, since they hang off `ModConfigScreen`, which is itself a native options screen.

  **Importing is additive and deduplicated, and it is the only mode the screen offers.** `WaypointStore.mergeFrom()` adds only the incoming waypoints not already present under the same identity - name, exact position, and dimension (as `dimensionOrOverworld()`, so a file old enough to have none matches the Overworld) - and never replaces or removes anything from the current world's list, because a `waypoints_*.json` may be the only copy of some player's waypoints and a destructive import is not a risk worth offering a button for. This identity check is deliberately *not* the name+X+Z (no Y) rule `XaeroSync`/`XaeroWaypointFormat` use for their own dedup: that rule exists only to work around an Xaero waypoint saved without a Y coordinate reporting a synthetic `y = 64`, which is irrelevant here - both sides of this merge are this mod's own JSON, where Y is always real, so throwing that precision away would just make two waypoints at different heights on the same column look identical. `focused` is cleared on the copy as well, since focus is exclusive and an imported focused waypoint would sit beside the current world's own. `favorite` is kept on the copy: unlike focus it is the player's own mark on the waypoint, not state tied to the world it came from. `death` and `fastPing` are always cleared on the copy that gets added, the same way `WaypointCreateScreen.saveWaypoint()` already clears them the moment either kind of waypoint is edited by hand (see Data model above): a death waypoint's dwell-timer deletion and a Fast Ping's numbering both belong to the world that created them, and carrying either into a new world would either delete the import for no reason or miscount the next Ping without a matching death/ping ever happening there.

  **The import button is the first row of `ModConfigScreen`: one full-width vanilla `Button`, with no section header, the way vanilla's options screens lead with their sub-screen buttons. It is added through `addSmall(List<AbstractWidget>)`, not `addBig`, because 26.1's `OptionsList.addBig` only takes an `OptionInstance<?>` (the single-widget overload came later).** `addSmall(List)` exists on all three versions and lays its widgets out from the row's left edge (`centerX - 155 + i * 160`). So one widget `BIG_BUTTON_WIDTH` (310, `getRowWidth()`) wide spans the row exactly, as `addBig` would.

  **Both the import button and `ImportConfirmScreen`'s confirm button are greyed out outside a world** (`WaypointStore.isInWorld()`), with a tooltip saying to join one first (`easywp.config.import_needs_world`); the confirm handler also re-checks before merging. Mod Menu reaches `ModConfigScreen` from the title screen, and an import there used to merge into whatever list the last world had left in memory, save nothing (`getWorldId()` is `unknown`), and still report "N imported".

  Loaded lazily — `WaypointStore.checkAndLoadWorldWaypoints()` runs every render frame, but the actual `getWorldId()` computation inside it is gated on `client.level` having changed identity since the last check (true on join/dimension-change, never on an ordinary frame), so the file is only re-read when `worldId` changes. **Leaving a world drops it**: an `END_CLIENT_TICK` handler in `EasyWpClient` calls `WaypointStore.forgetWorld()` whenever `client.level` is null, which releases `lastCheckedLevel`, resets `lastWorldId` and clears the list (a no-op once there is nothing left). `lastCheckedLevel` used to keep the old `ClientLevel` — every loaded chunk and entity — alive in the main menu until the next world, and the stale list with it. Rejoining therefore always reloads from disk (`readWaypointData` flushes pending saves first), including rejoining the same world, which used to skip the reload. A dimension change never passes through a null level (`ClientPacketListener.handleRespawn` swaps it directly with `setLevel`), so it does not trigger this; a server reconfiguration does (`clearClientLevel`, e.g. a proxy moving the player to another backend). A tick rather than `ClientPlayConnectionEvents.DISCONNECT` because the tick is guaranteed to run on the client thread, the only one that may touch the list. None of this is synchronized, deliberately: every caller — `render()`, `DeathWaypointManager.tick()`, and the screens — runs on the client thread, and so does every mutation of the waypoint list. A `synchronized` block used to wrap just the reload while the rest of the list was mutated freely without it, which bought nothing and implied a thread-safety guarantee the class never had; it was removed rather than extended. Saved with Gson pretty-printing immediately after any mutating action (create/edit/delete/visibility/focus/share) — no periodic autosave. The document is serialised on the client thread at that moment, but written by `AsyncJsonWriter` (see below). **Old shared waypoints are split on load.** `WaypointStore.toWaypoints` turns every entry saved with `shared: true` into the waypoint itself plus a copy at `convertedPosition()` in `pairedDimension()` — exactly where its mirror used to be drawn — right after it: same name, colour, visibility, favorite and creation time, never focused (focus is one waypoint) but kept visible beside the original's focus as the mirror was, never a death waypoint or Fast Ping. The copy is skipped when the file already holds a waypoint of that name at that exact spot, or when the shared one was outside the pair. The current world's file is written straight back after a split (its `.bak` keeps the old shape) and an INFO line is logged; another world's file read by the import picker is split in memory only, and `countWaypointsIn` counts after the split so the picker and the confirmation agree. `shared` is read but never written (a `Boolean` left null, which Gson skips), and versions before 1.4.0 read the missing key as `false`. Splitting rather than just dropping the flag is what keeps a previous Xaero Export intact: the copy carries exactly the identity (name, X, Z in the other dimension) the shared waypoint's second image had in Xaero and in the link ledger, so the next Export does not delete it there. `visible`/`focused` are optional/nullable in the JSON for backward compatibility with older save files, and so is `forceVisible`, saved since 1.4.0 so the waypoints kept visible beside a focused one survive a restart the way the focus always did. It is written as `false` whenever nothing is focused (`WaypointData(wp, anyFocused)`): deleting the focused waypoint — from the list, by reaching a death waypoint, by a Xaero import — leaves the others' flags set in memory, where they are ignored until the next focus clears them, and they are not written out as if they still meant something. `favorite` (since 1.4.0) is optional the same way.

  **A deletion from the list waits 7 seconds before it is final**, each on its own clock, and the waypoint stays in its place in the list meanwhile. `WaypointStore.markForRemoval` sets the waypoint's `pendingRemoval` flag, starts its countdown in a `PendingRemovals` and saves; from that moment it is gone everywhere but its row — `isShown` is false (not drawn), `hasAnyFocused` ignores it (a focus it held is gone too), `saveToFile` leaves it out (so closing the game meanwhile keeps it deleted, as a deletion always was), and `mergeFrom`'s identity check skips it. `undoRemoval` clears the flag and saves, putting it back exactly as it was, focus and all; `removeNow` makes it final at once. `tickPendingRemovals`, run every client tick in a world, drops the ones whose time ran out from the list and bumps `removalsVersion`, which an open list checks in its `tick()` to rebuild its rows. The countdowns live in `WaypointStore`, not on the screen, so closing and reopening the list within those seconds still shows the rows; they are cleared on every world change (`loadFromFile`, `forgetWorld`), and a Xaero Import or Export makes them all final first (`commitPendingRemovals`), since a sync acts on the list as it is about to be. Only the list deletes this way — a death reached, a Xaero import, death eviction and `/easywp remove` go through `WaypointStore.remove`/`removeAll`, final at once: it also ends a pending deletion of the same waypoint and bumps `removalsVersion`, so an open list drops the row instead of offering Undo or edit for a waypoint that is gone. `DeathWaypointManager` ignores death waypoints pending deletion, both when evicting and when timing an arrival.

  **A waypoint's copy in the other dimension is recognised, so duplicating never makes two.** `WaypointStore.findCopyInPairedDimension` looks in the other half of the pair for a waypoint with the same name whose X/Z correspond at 1:8 — `PairedCoordinates.areCopies`, which compares in Nether coordinates so it works in both directions despite the rounding (`-15` in the Overworld copies to `-2`, which copies back to `-16`; all three pair). Y is not compared, so a copy whose height the player adjusted is still the copy; a renamed or moved one, or one pending deletion, is not. `duplicateIntoPairedDimension` returns `null` instead of adding a second copy, and both places that offer it (the list's "More options" menu and the create screen's "Save and duplicate") grey it out while the copy exists. Delete the copy and duplicating works again.
- **Global mod settings**: `config.json`, independent of any world, managed by `ModConfig` (marker size/opacity, label uppercase/distance, death-waypoint enable + `maxCount` + arrival radius + grace seconds, visibility persistence, ping raycast range/fluids/follow-render-distance (shared by classic Ping and Fast Ping - one `ModConfig.Ping` group, one "Ping/FastPing" section header in `ModConfigScreen`, not two), waypoint-list sort mode, Xaero integration enable + chat-format, label distance in kilometres (`labelDisplay.metersOnly`, inverted so that Gson's `false` from an older file means the default, kilometres on) and the maximum of waypoints drawn (`visibility.maxVisible`, where Gson's `0` is the default, no limit), plus `onboarding.lastSeenVersion` (the welcome message, a group of its own so an older config shows it once) and `favorites.unlookedOpacityPercent` (80) — a group of its own, since inside `lookAt` a config.json from before it would read 0% and every favorite would vanish when not looked at. There is no delete confirmation any more: the `confirmations` group (`confirmBeforeDelete`) went in 1.4.0-beta.2, since a list deletion can be undone for 7 seconds, and Gson ignores the key in an older file. Grouped by feature into nested classes so new settings groups don't reshape the file; each group is null-checked on load for backward compatibility with older `config.json` files. A group *added later* (like the two above) gets its defaults from its own field initializers via that null-check; a field added to an *existing* group instead gets Gson's zero value for a JSON that predates it — which is why a new setting whose sane default isn't `false`/`0` belongs in a new group, never bolted onto an old one.

- **Per world/server, hidden groups**: `groups_<worldId>.json`, `{"hidden": [...]}` — the groups hidden with the list's eye (see Groups below). Kept apart so `waypoints_*.json` keeps the array shape older versions read; a missing or unreadable file only shows groups, never hides one. Loaded with the waypoints, dropped by `forgetWorld`, written through `AsyncJsonWriter` whenever a group is hidden or shown, and pruned on every waypoint save to the groups that still exist.
- **Per world/server, Xaero link ledger**: `xaero_links_<worldId>.json`, managed by `XaeroLinkLedger` — one `dimension|x|z|name` identity per entry for every waypoint easyWp and Xaero have actually exchanged, which is what lets the two sync buttons propagate deletions without touching waypoints only one side ever had. Written only by those two buttons (see Xaero's Minimap integration below), read fresh on each press rather than cached, and safe to delete: an absent ledger just makes both buttons additive again.

All four stores go through `JsonStore` (in `common/`) rather than writing straight to their destination: the document is serialized in full, written to a sibling `.tmp`, forced to disk, and then moved onto the target atomically, so a crash mid-save can no longer truncate a file that is the only copy those waypoints exist in. Every successful write first snapshots the previous revision to `<file>.bak`, and every load falls back to that snapshot when the main file is missing, empty, or unparseable. **Waypoint and config saves are written off the client thread by `AsyncJsonWriter.SHARED` (in `common/`).** Every save used to run `JsonStore.write` inline, fsync included, which is a felt stall on a slow disk: a Fast Ping, a death, or a config slider (one save per step) each waited for the disk mid-frame. Now the caller serialises the document on the client thread (so exactly the saved state is written, and the waypoint list is never read from another thread) and hands it to one daemon thread. Saves **coalesce** per file: a newer document replaces one still waiting, so a burst of slider steps costs one extra write, and the file still ends at the newest state. `flush()` blocks until everything handed over is on disk. `WaypointStore.readWaypointData` flushes before every read (rejoining a world just left, the import picker's counts), and `EasyWpClient` flushes on `ClientLifecycleEvents.CLIENT_STOPPING`, since the daemon thread would otherwise be cut off at exit. A failed write is logged and does not stop the queue; the file's next save retries with its newer document. Nothing can leave `flush()` waiting forever, which used to freeze the game on joining a world or on exit: `drain()` clears its `draining` flag in a `finally` when an `Error` escapes the sink (the normal, empty-queue exit still clears it inside the same lock hold that found the queue empty — clearing it in the `finally` there would let a concurrent `write` see the flag still set, skip scheduling, and strand its document), and `write()` clears it again if `execute` itself throws. Anything still queued after either is scheduled by the next save. `XaeroLinkLedger` and Xaero's `waypoints.txt` fallback still write synchronously: they only run on a button press, and the ledger is read back within the same action.

`ModConfig` deviates in one place on purpose: if neither the config nor its backup can be read it runs on in-memory defaults **without** saving, because writing would push the unreadable file into the backup slot and destroy the last good revision. `common/src/main/java/com/easywp/XaeroWaypointFormat.java` is the other class (besides `JsonStore`) living in `common/` for the same reason: it is pure text handling (Xaero's `waypoints.txt` line format, read from that mod's own bytecode rather than guessed — see Xaero's Minimap integration below), nothing `net.minecraft.*`, so it compiles standalone and every version shares it unmodified. `common/src/test/` holds eleven suites (see Tests above), all run by `:common:test`.

### Rendering — one HUD renderer, shared by every version

Since 1.3.4 every waypoint — marker icon, label backdrop and label text — is projected from its world position to screen coordinates and drawn in 2D during the **HUD pass**, the same way Xaero's Minimap draws its in-world waypoints (confirmed from its 26.5.0 bytecode: a mixin captures the projection in `GameRenderer.renderLevel`, and a HUD mixin projects each waypoint with `Vector4f.mul(matrix)`, divides by `w` and draws in 2D). `WaypointRenderer` is one shared file; there is no world-pass rendering, no `RenderType`/`RenderPipeline`, no Iris integration and no shaderpack detection left anywhere in the mod.

**Why not in the world.** Up to 1.3.3 the waypoints were 3D billboards drawn during the world pass (`END_MAIN` on 26.1, `COLLECT_SUBMITS` on 26.2/26.3), and three problems followed from that, none fixable in place:
- **Translucents.** A see-through label either writes depth or it doesn't. If it does (what 1.3.3 did, to stop clouds and water painting over it), water, clouds, ice and glass drawn later fail their depth test behind it and vanish, leaving a hole that shows the terrain behind them. If it doesn't, those translucents paint over it. The HUD shares no depth buffer with the world, so neither can happen.
- **Shaderpacks.** Anything drawn in the world pass goes through Iris's gbuffers programs — lighting, lightmap, fog, tone mapping — which turned the white label text grey under Complementary. The HUD is drawn after Iris's final pass, so it is untouched without any detection or special case.
- **Alignment.** Under shaders the backdrop was pushed 0.005 behind the glyphs to stop z-fighting, on a billboard only 0.25 blocks from the eye. That is a 2–3% depth difference, and after the perspective divide the backdrop slid toward the screen centre, worse the further off-centre the waypoint was. In 2D the backdrop and text share one pose.

The cost is that waypoints are always visible through terrain, which the see-through 3D version already was.

**Projection — exact, current-frame, no lag.** `GameRenderer.extract` fills the frame's `CameraRenderState` (`extractCamera`) *before* it extracts the GUI (`Gui.extractRenderState`), in all three versions. So the HUD reads exactly the camera the world is about to be drawn with this frame: the interpolated position (partial tick), `viewRotationMatrix`, and a `projectionMatrix` that already carries dynamic FOV (sprint, spyglass, zoom mods). Capturing the matrix in `renderLevel` instead, as Xaero does, would be one frame late here, because the world renders after the GUI is extracted. What the camera state lacks is the view bob and hurt tilt, which `renderLevel` multiplies into a local copy of the projection. `WaypointRenderer.applyBob` reproduces that by calling the same private `GameRenderer.bobHurt`/`bobView` (26.x runs on Mojang names, so the lookup is stable; the signature is `private void (CameraRenderState, PoseStack)` in all three versions). They are looked up once with `getDeclaredMethod` + `setAccessible` and turned into `MethodHandle`s with `unreflect`, then called with `invokeExact` every frame — `Method.invoke` used to box the arguments into a fresh array and re-run the access check each frame. Any `Throwable` from the call disables the bob for the session, as `Method.invoke`'s `InvocationTargetException` effectively did. Both are pure functions of the already-extracted state, so the clip transform is vanilla's own `projection × bobHurt × bobView × viewRotation`. If the lookup ever fails, the waypoints are projected without bob and a warning is logged once. Iris moving the bob to the model-view under a shaderpack produces the same image, so it needs no special case. The nausea/portal screen warp is not reproduced. A point with clip `w ≤ 1e-4` is behind the camera and skipped.

**Size — same as the 3D version.** The marker's world size is unchanged (`WAYPOINT_MIN_SIZE`, growing by `WAYPOINT_VISUAL_ANGLE` per block past 2 blocks, times the size setting), sized at the distance clamped to the render distance. It converts to GUI units through `projectionMatrix.m11() × guiHeight/2 / depth`, with the depth taken from clip `w` at the clamped distance. That is exactly what the billboard projected to. The result does not depend on the GUI scale (it is angular) and does follow the FOV. The marker is bottom-centred on the projected point. The label sits above it at the 1.3.3 ratios: one font pixel = `0.05 × markerHeight` (so the 9px line is 0.45×, which `WaypointCreateScreen`'s preview reproduces), with a gap of `0.05 × markerHeight` above the marker.

**Text.** The glyph scale is a continuous `0.05 × markerHeight`, and the origin follows the projected point unsnapped, so the label scales and moves as smoothly as the marker and keeps its exact ratio to it. Rounding the scale to whole physical pixels per font pixel (and the origin to the pixel grid) was tried in 1.3.4 for crisper glyphs and reverted: the label grew in visible steps, its size drifted relative to the marker, and it moved in 1px jumps. Text is `#FFFFFF`, no shadow. The backdrop is Font's own background box (`x-1..x+width`, `y-1..y+9`) in the same scaled pose, filled with `UiPalette.LABEL_BACKDROP` (`0x40000000`), which the create screen's preview also uses. The distance suffix is `DistanceFormat.format`: whole metres below 1000 (`(999m)`), kilometres with one truncated decimal from there on (`(1.2km)`, built by hand so the separator is a point in every locale), or metres throughout with `labelDisplay.metersOnly`. The per-waypoint label cache is keyed on `DistanceFormat.cacheKey` rather than the metres, so in kilometres the label is rebuilt and re-measured every 100 blocks instead of every block.

**Fade when not looked at.** A waypoint the player is not aiming at is drawn at `ModConfig.lookAt.unlookedOpacityPercent` (default 50% opacity; 100 turns the fade off): marker, backdrop and text alike. "Aiming at" is judged against the waypoint's **marker alone**, expanded by a margin, in fractions of the screen height — never its label, or a long name would make a bigger target. Using the marker's rectangle rather than its point means a near waypoint whose icon fills half the screen counts as looked at anywhere on it.
- **Margin:** `LOOK_MARGIN` = 1.5% on both axes, scaled by the area size.
- **Fade:** past the margin the waypoint smoothstep-fades over a band (`LOOK_FADE` 3%), so sweeping the view across it eases in and out.
- **Area size:** `ModConfig.lookAt.lookAreaSize` (1–4, default 2) scales the margin by `LOOK_AREA_SCALE` (0, 0.5, 1, 2): 1 is the marker itself and nothing more, 2 just a little around it. `ModConfigScreen` offers it as a discrete slider (step 1), with a tooltip, and the opacity as a slider in 5% steps, both in the "Waypoint Appearance" section.
- **Nearer covers farther:** `computeLook` walks the drawn waypoints nearest first and stores each one's 0–1 `look` on its holder; once the crosshair is inside one waypoint's margin box, every farther one counts as not looked at. Of two markers partly in front of each other, the farther lights up only where the nearer does not cover it. It runs after the visible limit, so only drawn waypoints cover others. (Until 1.4.0-beta.2's second round the rectangle included the label, margins were 1.5%/4% and fades 3%/6% per axis, and overlapping areas each lit up on their own.)
- **Config group:** `LookFade` is a group of its own, not fields on `WaypointSize`, because neither default is Gson's zero value (see Persistence). It is saved under `lookAt` since 1.4.0-beta.2: the area went from seven sizes (1–7, default 3) to four with another meaning and the opacity default from 60% to 50%, and a renamed group is the only way an existing config picks up new defaults (a group that is present keeps what it saved). The old `lookFade` key is ignored and dropped on the next save, a customised value with it.

A **favorite** fades to `ModConfig.favorites.unlookedOpacityPercent` (default 80%) instead of the normal setting — its own value, not a multiplier on the other. The marker's own opacity setting multiplies with the fade. A **focused** waypoint (the list's highlight) skips the fade entirely: it is drawn fully opaque wherever it is on screen for as long as it stays focused, since it is the one the player asked to follow. Waypoints kept visible alongside it (`forceVisible`) still fade normally.

**Layering.** Waypoints are drawn far to near, with `nextStratum()` after each one. The GUI renderer draws every text of a stratum after every quad of it, so without a stratum per waypoint a farther label's text would land on top of a nearer marker. The last `nextStratum()` also keeps the vanilla HUD elements drawn afterwards above the waypoints.

**Visible limit.** That stratum per waypoint is a draw batch per waypoint, which is what makes hundreds on screen expensive. `ModConfig.visibility.maxVisible` (0 = no limit, the default; 5–100 in steps of 5 in `ModConfigScreen`) keeps only the nearest N in `applyVisibleLimit`, which runs on the far-to-near list *after* the off-screen ones are already gone — so the limit counts what is on screen, and turning around brings the nearest ones in that direction into view instead of slots being held by waypoints behind the player. A focused waypoint is always kept, inside the N, so the cap holds exactly.

**Hooks and F1.** `EasyWpClient` attaches two Fabric HUD elements:
- one before `VanillaHudElements.MISC_OVERLAYS`, so waypoints sit under the vignette, spyglass scope, crosshair, hotbar and chat as if they were part of the world;
- one before `SLEEP`, because vanilla skips every HUD element while the HUD is hidden (F1) *except* the sleep overlay.

Each draws only in its own half of `ClientCompat.isHudHidden()`, so waypoints stay visible under F1 exactly as the world-rendered ones were. With a screen open the HUD is still extracted behind it, and in-game screens blur it along with the world. The HUD is not extracted on the level-loading screen.

### UI

Hand-built on vanilla `Screen`, no third-party UI toolkit. Shared widget is `ModernButton` (fluent builder: `ModernButton.modernBuilder(...).pos(x,y).size(w,h).icon(painter).build()`; the optional `IconPainter` draws the button's icon inside the button's own render pass, from its own position, so icon and hit box cannot drift apart. Every icon button in `WaypointListScreen` uses it, from the row actions and focus swatch to the sort glyph and corner buttons; the screen used to draw all of them separately at hand-mirrored coordinates; whether the message has text to draw is kept in a field, set by the constructor and by its `setMessage` override, instead of resolving the message to a string every frame just to find out it is empty), with normal/hover/disabled states in a near-black translucent palette centralized in `UiPalette` (color constants only, no Minecraft imports, so it stays trivially byte-identical across versions). GUI icons under `textures/gui/` are drawn as plain white masks and tinted at draw time via `Icons`' `drawMarkerIcon` helper (`drawStar` and `drawMoreGlyph` are hand-drawn with `fill`) and the tinted 11-arg `GuiGraphicsExtractor.blit(..., int color)` overload (multiplicative: `result = texture × color`), rather than baking color into each PNG — this is also how the waypoint-list marker swatch and the focus button get colored with the waypoint's own ARGB color instead of drawing a flat `fill()` square. Three screens:
- `WaypointCreateScreen` — create/edit modal (name — for a new waypoint the field starts empty and shows the default `Waypoint N` as a grey `EditBox` *suggestion*, not a hint, because vanilla hides the hint while the box is focused and this one always is; typing replaces it outright and an empty name still saves as that default — resolved once per `init()` into a `defaultName` field that the suggestion, the live preview and the save all read, rather than translated again every frame for the preview; the screen overrides the no-argument `setInitialFocus()` to focus the field, so the name can be typed without clicking it; calling `setInitialFocus(nameField)` inside `init()` does not work, because vanilla calls the no-argument version right after `init()` and, when the screen was opened from the keyboard as N/H always are, it tab-navigates one step on and takes the focus away again, X/Y/Z, two-bar color picker, Enter-to-save; the name field is 204px, the width it used to share with the portal toggle). The name is saved without surrounding spaces, and one that is only spaces counts as empty (the default name, or the old name when editing). A new waypoint's dimension is fixed when the form opens, so crossing a portal with it open does not file it on the other side. Saving an edit whose waypoint left the list meanwhile (a death waypoint reached with its form open) puts it back rather than editing an object nothing holds. The X/Y/Z fields read through `RelativeCoordinate`: a number, or `~`/`~5`/`~-3` relative to the player's exact position on that axis (floored to a block by `BlockPos.containing`, as vanilla's block-position arguments do); a field that cannot be read — and now also `NaN`/`Infinity`, which used to become 0 or `Integer.MAX_VALUE` — keeps the coordinate the form opened with. **The default name** is `WAYPOINT #N` with the lowest N whose exact translated name no waypoint of the player's dimension uses, tried name by name through `NameNumbering` rather than read back out of existing names, since Fast Ping's `Ping #N` shares the `#N` shape; it used to be the total count + 1 across all dimensions, which repeated names after a delete. **Two pages.** The main one is full (the modal is 224px tall), so a second page, "More options", holds the favorite toggle and "Save and duplicate in the Nether/Overworld" (named after the other half of the pair from the waypoint's dimension — the player's own for a new one). A `⋯`/`‹` button in the bottom row (between Save, now 158px, and the list button) switches pages via `rebuildWidgets()`, and Esc on "More options" steps back to the main page, the way Esc leaves a vanilla options sub-screen. Cancel, save, the page button and the list button are the same on both pages, and saving from either saves everything: every value lives in a field of the screen, and the four `EditBox`es are created once (`createFields`) and only repositioned on later `init()` calls, the way the list keeps its search box — they used to be rebuilt in `init()`, which also lost what had been typed on a window resize or on coming back from the list. The colour bars' active family is seeded there once too. The duplicate saves the form first, then adds an independent copy through `WaypointStore.duplicateIntoPairedDimension` (same name and colour, at `convertedPosition()`, new creation time, nothing else carried over) and closes; it is greyed out with a tooltip outside the pair or while the copy already exists (see Persistence). It is offered for a new waypoint too, so the copy is made in the same step as the waypoint; `saveWaypoint()` returns the waypoint it saved for exactly that, and the duplicate is judged on it after the save. The overlay message after it (`announceDuplicate`, shared with the list's menu) says where the copy went, or that it was already there when the save changed nothing about that. **Where it goes back to:** an optional `returnScreen`, set when the form is opened from `WaypointListScreen` (edit or New). Then save, cancel, Esc (all through an `onClose()` override) and the form's own list button return to that same list, which rebuilds its rows in `init()`; opened from the game (N/H) they close to the game, and the list button opens a list whose Back returns to the form, as before. The list button used to always open a *new* list with the form as parent, so list → edit → list → edit stacked screens. The palette data and its random-pick helper (`WaypointColors.random()`, the screen's own starting selection) live in `WaypointColors` rather than here, extracted once Fast Ping needed the same colors with no picker UI to offer one through. The same constructor path is used to pre-fill coordinates from the player's feet (`N` key) or from a crosshair raycast (`H` key, see `WaypointPing`) — the screen itself is agnostic to where the `BlockPos` came from. `key.easywp.fast_ping` bypasses this screen entirely (see Keybindings above).

  **The color picker has gone through four designs across this project's git history, each correcting something the previous one got wrong.** The original was a flat 15×4 grid (60 colors: grayscale + 14 hues, × vivid/light/deep/dark). That grid was *densified* to 28×7 (196 colors) by inserting an RGB midpoint between every adjacent pair of hues and shades, on the theory that "similar colors near each other" meant making the whole grid one continuous gradient - which instead made most of it near-duplicate shades of the cell right next to it, worse at the one thing a picker has to do well: letting the player tell two colors apart at a glance. That was replaced by 20 maximally-distinct base colors (18 hues 20° apart + white + black) in a 4×5 grid, paired with a second, smaller grid showing 7 shades of whichever base was active - better separated, but the two grids side by side read as loosely related rather than as one control, the "active family" indicator borrowed the same gold used elsewhere for a focused waypoint (a collision in meaning), and 7 shades was thin for a real dark-to-light ramp.
  
  **The current design (`WaypointColors.FAMILY_BAR`/`HUE_FAMILIES`/`GRAYSCALE_FAMILY`) is two touching horizontal bars, stacked, framed separately.**
  - **The top bar is 14 family colors: 12 hues spaced exactly 30° apart around the color wheel (12 × 30 = 360, dividing evenly, same reasoning as the 18-hue version's 20° spacing but wider so the hues read as more obviously distinct - a direct response to the 20-base design's hues still doubling up visually) plus white and black.** `WHITE_INDEX`/`BLACK_INDEX` are the two flat indices (12, 13) past the 12 hues. The 14 swatches sit flush against each other, no gap - `FAMILY_SWATCH_W` is `PICKER_WIDTH` (210) divided evenly by 14 (15px each). Each hue swatch is `HUE_FAMILIES[i][6]`, not the fully saturated, fully bright vivid tone at index 7 - full brightness at full saturation is the single "loudest" point on the whole ramp, and 12 of them side by side read as garish rather than as a calm set of families to choose from. One step back (still full saturation, brightness pulled in by about an eighth) keeps each hue clearly identifiable without going far enough to look muddy. White and black are left at their own extremes, since neither is a saturated color with a "loud" version to soften.
  - **The bottom bar is `WaypointColors.SHADE_COUNT` (15) shades of whichever family is active, also touching, strictly dark (left) to light (right).** Each hue's row is built as two halves meeting at the middle index: index 0..7 darkens toward the vivid tone by raising brightness at full saturation (shades, mixing in black), index 7..14 lightens past it by lowering saturation at full brightness (tints, mixing in white) - so the vivid tone anyone would call "the" red/blue/etc. sits exactly in the middle, not smeared across a whole plateau. `SHADE_SWATCH_W` is the same 210 divided evenly by 15 (14px each) - the two bar widths agreeing on 210 rather than one deriving from the other is what keeps them the same total width without either one picking an odd swatch size to make it work. White and black share one family: the plain grayscale ramp (dark to light, same direction as every hue row), since neither has a hue of its own to shade or tint.
  - **`BAR_HEIGHT` (15) matches `FAMILY_SWATCH_W` exactly** - the top bar's swatches are square, and the bottom bar's own 14px-wide ones are one pixel off square, close enough to read as the same shape. (An intermediate value of 17 was tried first and judged still too tall to read as "almost square.")
  - **Touching swatches change how selection has to be drawn.** A swatch with no gap on either side can't take an *outer* ring the way the previous designs' spaced-out swatches could - it would paint over the neighboring color. `drawColorSwatch` instead fills the whole cell edge-to-edge with no inset in the normal case (so the bar reads as one continuous strip), and draws the selection mark as a 2px inset frame when it's the exact selected color.
  - **Every accent border in the picker is the same fixed `UiPalette.MODAL_BORDER` color** - the exact-selection frame on either bar, and the "this family is active, but not the exact selection" mark on the top bar, all draw in it, and so does the frame around each bar. Two earlier attempts used white for the selection frame and a separate blue (then briefly gold, which collided with the unrelated meaning `FOCUS_OUTLINE_ON` already carries elsewhere in this UI - a waypoint's own *focused* state) for the active-family mark; a highlight whose color depended on which of the two states was showing read as inconsistent. Tying every one of them to the same constant the bars' own frame already uses means the picker's accent color literally cannot drift out of sync with itself again.
  - **Each bar gets its own 1px border frame, 2px outside its own bounds, filled before the swatches are drawn on top of it.** With no internal gaps left inside either bar to hint that "this is one control," and both bars sitting one above the other, the frame plus the gap between them is what keeps a player from reading the whole thing as a single undifferentiated block of color.
  - **Clicking a top-bar swatch selects it outright and switches the bottom bar to that family; clicking a bottom-bar shade changes the selected color without changing which family is shown** - `activeBaseIndex` (which family the bottom bar is browsing) and `selectedColor` (what will actually be saved) are deliberately two separate pieces of state, because after picking a shade they disagree on purpose: the active family's own top-bar swatch is not necessarily the selected color anymore.
  - **The bottom bar's `SHADE_COUNT` buttons are created once and never rebuilt when the active family changes.** Each one closes over its own fixed slot index and looks up `WaypointColors.familyOf(activeBaseIndex)[slot]` at click time rather than capturing a color value at creation time; the render loop does the same lookup every frame. Switching families is therefore just mutating `activeBaseIndex` - no widget list surgery, unlike `WaypointListScreen`'s `refreshItemWidgets()` pattern used elsewhere in this codebase for a dynamic row count.
  - **`WaypointColors.nearestMatch(int)` is what makes editing an existing waypoint (or Fast Ping's own `random()` pick) show a coherent picker state**, since a waypoint's stored color need not be exactly one of the palette's own values - an older save file, or a color from before this redesign. It searches every shade of every family for the nearest RGB match, not just the 14 top-bar entries, specifically so a waypoint saved deep in a hue's dark end still activates *that hue's* family instead of the objectively-closer-in-raw-RGB-terms black.

Row order is driven by `WaypointSortMode`, cycled with the button beside the search box and persisted in `ModConfig.list.sortMode`; its default `CREATED` sorts by `createdAtMillis` with a stable sort: waypoints from before 1.4.0 all read 0, so they keep their insertion order among themselves and come first — where the mode's old "no sort at all" put them — and a waypoint imported from another world sorts by when it was originally created, not when it was imported. The action-icon strip is built right-to-left from `centerX + 120`; TP is the one *conditional* icon in it (gated on the permission above) and is deliberately the innermost (`centerX + 40`), so every icon's position stays fixed regardless of whether the player has the permission. `NAME_MAX_WIDTH` (155) runs up to just short of it — the share button that sat between edit and "More options" moved into that menu in 1.4.0, the icons closed up rightwards, and the name took the room. Vanilla strips the section sign from chat text a player sends before broadcasting it, a long-standing anti-spoofing measure with no client-side opt-out, so no client mod - this one included - can make the dimension word render in `DimensionNames.color()`'s green/red/purple for *other* players reading it in chat. The format still encodes the dimension as plain text at a fixed position, which is the most useful approximation reachable without a server-side companion or falling back to the Xaero-recognized line (`xaeroChatFormat`, unaffected since that one is parsed and re-rendered by Xaero's own client, never shown as raw chat text).

  - **`OptionsSubScreen.list` is null until `init()` runs.** It is declared `@Nullable` and only assigned inside `addContents()`, which `init()` calls — and `init()` is called by `setScreen` (`ClientCompat.setScreen`), not by the constructor. Every "Reset" button and the ping follow-render-distance toggle go through `reopen()`, which rebuilds the screen to pick up the new value; it must therefore set the new screen **first** and restore the carried-over scroll position **after**, or it dereferences null. (It did exactly that until 2026-08-28, so every Reset click crashed the game.) Setting it first is also what makes `setScrollAmount` meaningful — it clamps against `maxScrollAmount()`, which is 0 on a list that has not been populated yet.
  - **`removed()` is overridden to do nothing**, on purpose: `OptionsSubScreen`'s default re-saves vanilla's own `options.txt` on close, which this screen never touches.
  - **`addContents()` is overridden rather than inherited** so the `OptionsList` can be constructed with `LIST_WIDTH` (330) instead of the full screen width. `OptionsList.getRowWidth()` is hardcoded to 310 and the scrollbar sits at `getRowRight() + margin`, so passing the window width would strand the scrollbar at the far right edge, nowhere near the rows. ### Death waypoints

`DeathWaypointManager` needs no mixin. It combines two signals, because neither covers every case alone:
- **The alive→dead edge of `isDeadOrDying()`**, sampled each client tick. It fires as the death screen appears, at the dead player's own position, which does not move until the respawn packet arrives. It is what records a death even if the player disconnects from the death screen. A player instance that is already dead when it appears (joining on the death screen) is marked handled, not recorded.
- **`Player.getLastDeathLocation()` changing.** The server sends the exact death `GlobalPos` in every login and respawn packet (it is what the recovery compass uses). With `doImmediateRespawn` the player dies and respawns inside one server tick, before the health drop is synced, so the client never sees it dead and the edge never fires. A tick-based check of the old `LocalPlayer` instance was tried first and did not work for exactly that reason. The location change is the signal that still arrives.

A death recorded by the edge sets `edgeRecordedPendingRespawn`, so the location change its own respawn brings is not recorded twice. The location is checked *before* the player-instance change within a tick, because a normal respawn delivers both together. The first location seen after joining is only a baseline, never a death. One accepted gap: dying twice on the same block with immediate respawn leaves the location unchanged, so the second death is not recorded.

On either signal it creates a black waypoint named from `easywp.death.name` plus the local `HH:mm`, after evicting the oldest existing death waypoints down to `ModConfig.deathWaypoints.maxCount - 1` (default `maxCount` is 1, which reproduces the original "only the latest death is kept" behaviour).

Deletion is a dwell timer, not a proximity trigger: a death waypoint is removed once the player has stayed within `radius` of it, in the same dimension, for `graceSeconds` **without leaving** — stepping out resets the timer. Each death waypoint keeps its own timer in a `Map<Waypoint, Long>`, so with `maxCount > 1` the player can walk through several and each expires on its own schedule; `dwellStart.keySet().retainAll(...)` drops timers for waypoints that were deleted or evicted meanwhile. Two deliberate details: arrival checking is skipped entirely while dead (the player does not control movement on the death screen, so sitting on the corpse before respawning must not count as arriving), and the manager calls `WaypointStore.checkAndLoadWorldWaypoints()` itself each tick, because the renderer skips that reload while display mode is `DISABLED`. Editing a death waypoint in `WaypointCreateScreen` clears its `death` flag, promoting it to a permanent waypoint so it stops being auto-deleted.

### Xaero's Minimap integration

easyWp can copy its own waypoints into [Xaero's Minimap](https://modrinth.com/mod/xaeros-minimap) (whose waypoints Xaero's World Map merely *displays* — it has no waypoint store of its own, so there is nothing to integrate with there directly) and copy Xaero's back. `xaerominimap` is a genuine `clientCompileOnly` dependency (not reflection — see `XaeroBridge` above), pinned per version in each `gradle.properties` — `26.5.0` for 26.1 and 26.2, `26.5.1` for 26.3, which is the only release published for it — from Xaero's own maven, which publishes Mojang-mapped jars per Minecraft version (`xaerominimap-fabric-26.1.2`, `xaerominimap-fabric-26.2`, `xaerominimap-fabric-26.3`) rather than the intermediary-mapped jars their public dev docs describe for `modImplementation` — confirmed by disassembling the jar's own bytecode, which references real names like `net/minecraft/resources/Identifier` directly, not obfuscated `class_NNNN` ones. That is what makes a plain `clientCompileOnly` dependency (no `mod*` configuration, matching how this project already declares Fabric API - see Entry points) link correctly against this project's own Mojmap-compiled code.

**Nothing in this integration runs on its own.** The whole surface is two buttons — `XaeroSync.importNow()` and `exportNow()` — wired to the pair in the bottom-right corner of `WaypointListScreen`. An earlier version pushed on every `saveToFile()`, imported on every world join, and polled `WaypointSet.size()` **every client tick** to pick up Xaero-side edits within ~50ms. All of that is gone: two lists that silently rewrite each other are hard to reason about, and everything the poll existed for a button press covers without needing an event Xaero doesn't expose anyway.

**Each button makes the target match the source — but only for waypoints the two have actually exchanged.** A sync adds what the source has and the target lacks, *and* removes what the target still has but the source has deleted. That removal is deliberately narrow: it only ever touches a waypoint recorded in `XaeroLinkLedger` as having existed on **both** sides. So a Xaero-only waypoint survives any number of Exports, an easyWp-only waypoint survives any number of Imports, and the player's two lists never clobber each other's private entries. Since identity is name + position, a *move* or *rename* in the source reads as a delete plus an add, so edits propagate too — not just creations and deletions.

**`XaeroLinkLedger` has to be persisted, not derived, and that is the crux of the feature.** It stores one identity per line that the two sides have exchanged, per world, at `config/easywp/xaero_links_<worldId>.json`. The reason it can't be computed on the fly: the moment the player deletes a waypoint in easyWp, nothing in the *current* contents of either list distinguishes "Xaero's copy of the thing I just deleted" (which Export should remove) from "a waypoint of Xaero's that easyWp never had" (which Export must not touch). The ledger is that distinction, written down before it's lost. It is read and written fresh on each press rather than cached — a handful of presses per session makes two small file operations free, and having no state means there is no per-world invalidation to get wrong on a dimension change or server switch. Losing or corrupting the file fails safe: an unreadable ledger reads as "nothing has ever been synced", which makes both buttons purely additive again, so it can leave a stale copy behind but can never delete something it shouldn't. `JsonStore` gives it the same atomic write + `.bak` recovery as the waypoint store.

**"Couldn't read" is never treated as "empty", and that guard is the one thing standing between this feature and real data loss.** Every read of the other side can come back `null` — no minimap session (main menu, between world loads), or a `waypoints.txt` that isn't where `guessedFile` guessed. If that were collapsed into an empty list, every linked waypoint would look deleted and a single click would wipe everything the two sides had ever shared. So `XaeroBridge.readRealWaypoints` returns `null` for "could not ask" versus an empty list for "asked, Xaero has none here", and a dimension that reads `null` is skipped whole: no adds, no removes, and **its ledger entries left exactly as they were**. The per-dimension granularity matters for the same reason — one unreadable dimension keeps its history while the rest of the sync proceeds. A dimension whose write fails is skipped the same way, so its ledger never claims a sync that didn't happen.

Two smaller pieces of the delete half are easy to get wrong:
- **Export visits every dimension in the ledger, not just the ones easyWp currently has waypoints in.** Delete the last easyWp waypoint in the Nether and the Nether vanishes from `groupByTargetDimension()` entirely — visiting only that map would leave its shared Xaero copies behind forever, which is precisely the deletion the button is for.
- **Import removes an easyWp waypoint only when its dimension was read and no longer holds it.** `XaeroSync.deletedOnXaerosSide` requires "was linked" and "its dimension was readable and the identity is gone". Every easyWp waypoint has exactly one identity on Xaero's side; until 1.4.0 a `shared` one had two (both halves of the pair), and the split of old shared waypoints on load (see Persistence) is what keeps those second images matched.

The old `Waypoint.fromXaero` flag is still gone, and is not what came back here: it marked *which* easyWp waypoints an automatic import had created, living on the waypoint and therefore dying with it — useless for Export, which needs the link to outlive the easyWp waypoint's deletion. That is the whole reason the ledger is a separate, waypoint-independent file.

**Export writes the player's own real waypoints, and that is a deliberate change from what it used to do.** The earlier version pushed into Xaero's `ThirdPartyWaypointManager`/`ThirdPartyWaypoints` layer — an API built for a mod to contribute map markers without touching anything the player placed by hand, which sounds like the safe choice and was the wrong one for this feature: that layer is pure runtime state Xaero never persists, so an exported waypoint **vanished on the next restart** and was drawn as a separate overlay rather than appearing in the player's own waypoint list at all, which is what "export to Xaero" has to mean. `XaeroMinimapBridge.addRealWaypoints` instead follows the sequence read from Xaero's own `xaero.hud.minimap.waypoint.DeathpointHandler.createDeathpoint` (the same problem: Xaero adding a real waypoint programmatically and needing it to survive a restart): resolve the dimension's `MinimapWorldContainer` the same way as before (`BuiltInHudModules.MINIMAP.getCurrentSession()` → `.getWorldManager().getAutoRootContainer()` → `.addSubContainer(...)`, per-dimension via `MinimapDimensionHelper.getDimensionDirectoryName(ResourceKey<Level>)`), then `world.getCurrentWaypointSet()` → `set.add(waypoint)` → `session.getWorldManagerIO().saveWorld(world)`. Four details there are bytecode-confirmed, not guessed, and each would be a silent bug if assumed:
- `saveWorld` declares a **checked `IOException`**, so it is caught inside `XaeroMinimapBridge` rather than at `XaeroBridge`'s edge, whose catch only covers `LinkageError | RuntimeException`. A failure there returns -1, which is what sends the caller to the file fallback — the waypoints are already in Xaero's in-memory set either way, so they are visible for the session regardless.
- `WaypointSet.add(wp, true)` **prepends**; the single-argument `add` appends. Export uses the latter, or easyWp's whole list would be inserted above the player's own waypoints in reverse order.
- `MinimapWorldContainer.addWorld(String node)` is get-or-create, and the right node name for a dimension with no world yet is `"waypoints"` — `MinimapWorldManagerIO.getWorldFile` derives a world's file name from its node and `loadDimensionFolder` names a node after the file it loaded, so that node is exactly the `waypoints.txt` Xaero itself would have written.
- The set to write into is whichever one is current, and `XaeroWaypointFormat.DEFAULT_SET_NAME` (`"gui.xaero_default"`, from `MinimapWorld.DEFAULT_SET`) is its name for the file fallback's `set` field. A set name Xaero doesn't have would still parse, but the waypoints would sit in a set the player has to go find before seeing any of them.

`XaeroMinimapBridge.applyRealWaypoints` does one dimension's adds and removes together, and three things there are each a bug done the obvious way: removals are collected during the `getWaypoints()` walk and applied strictly **after** it exits (`WaypointSet.remove` mutates the very list being iterated, so removing in place throws `ConcurrentModificationException` instead of removing); removals sweep *every* `WaypointSet` of every `MinimapWorld` in the dimension, because that is where `readRealWaypoints` found them and a waypoint the player filed in their own set must still be removable, while additions only ever go into the *current* set; and each changed world is saved exactly once, with the touched set collected rather than assumed to be one, since removals can land in a different world from additions.

All identity comparisons — the ledger, both dedups, and the removal match on both the live and file paths — use **name + X + Z**, deliberately ignoring Y: `readRealWaypoints` reports a synthetic `y = 64` for an Xaero waypoint saved without one (`isYIncluded()` false), so comparing Y would make those never match, duplicating on every Export and never matching on a removal. `XaeroWaypointFormat.removeAll` uses the same rule (`sameColumn`) rather than `merge`'s own `sameSpot`, which does include Y — the two would otherwise remove different things for the same click depending on whether the live bridge happened to be usable.

**The `waypoints.txt` file is the fallback, never a second writer.** Each operation decides *per dimension* whether the live bridge could actually do the work; only if it couldn't (Xaero missing, a binary-incompatible version, no active session, or its own `saveWorld` failing) does this write the file directly, as `removeAll` then `merge` in one write — never both paths for the same dimension, which is what avoids the real failure mode this split exists to dodge: Xaero rewriting its own `waypoints.txt` on save and clobbering a concurrent write from this mod. `merge` rather than the `replaceSet` the old continuous sync used: a sync's add half is exactly add-only and idempotent, and the delete half is now explicit in `removeAll` instead of implied by replacing a whole set. `replaceSet` was deleted along with the sync it existed for — it had been the production path and `merge` the tested-but-unused one, and that is now the other way round. `XaeroWaypointFormat`'s 14-field line layout (`waypoint:name:initials:x:y:z:color:disabled:type:set:rotate_on_tp:tp_yaw:visibility_type:destination`) and its 21-entry color palette (index = Xaero's own `WaypointColor` ordinal, used by both the live bridge and the file) were both read from `xaero.hud.minimap.waypoint.io.WaypointIO`'s disassembled bytecode, not guessed from third-party descriptions of the format (which disagree with each other and describe an older version — notably, the per-dimension folder name is `<namespace>%<path>` with `/` also replaced by `%`, not the `dim%N` scheme older write-ups describe; `XaeroSync.dimensionFolderName` reproduces that exactly, confirmed the same way). The one thing that genuinely isn't confirmed, because there is no live bridge to ask on this fallback path by definition, is the *world root* folder name (`Singleplayer_<name>`/`Multiplayer_<ip>`) — a standard, widely-documented guess rather than a bytecode-confirmed one; a wrong guess there costs nothing but a missed write, since easyWp's own JSON store remains the source of truth regardless.

**`XaeroBridge` is the only class allowed to be a no-op on Xaero's absence *or* its incompatibility**, and treats those as genuinely different failures — `isModInstalled()` and `isAvailable()` are therefore two different questions, not one with a convenience alias. `isModInstalled()` is just `FabricLoader.isModLoaded("xaerominimap")` (Xaero not installed at all — nothing in `XaeroMinimapBridge` is ever touched, so no `xaero.*` class is even resolved) and is what decides whether the Import/Export buttons appear. `isAvailable()` additionally requires a usable bridge, and is what decides whether an operation goes live or falls back to the file. The second failure is the one a compiled dependency has that reflection never did: the player can run an *older or newer* Xaero than the `26.5.0` this was compiled against, and a mismatched release missing a method/field this code calls produces `NoSuchMethodError`/`NoClassDefFoundError` — both `LinkageError`, which a plain `catch (Exception)` does **not** catch. Every public method on `XaeroBridge` therefore catches `LinkageError` as well as `RuntimeException`, logs once per session (not once per call), and disables the bridge for the rest of the session rather than retrying a failure that a version mismatch will reproduce identically every time. `disable()` deliberately does **not** clear the cached `modLoaded` — it once did, which meant an incompatible Xaero release made the mod look uninstalled, hiding the buttons in precisely the situation the file fallback exists for and making it unreachable.

**Import reads the player's own real waypoints**, manually created *or* landed via a chat-shared `[Add]` button someone clicked, from a `MinimapWorld`'s `WaypointSet`s (`XaeroMinimapBridge.readRealWaypoints`), skipping `isTemporary()` ones the same way Xaero's own `WaypointIO.saveWaypoints` excludes them from its file — they are pings and one-off destinations, not something the player asked to keep. It scans every known dimension (the vanilla three, plus anything easyWp already has waypoints in, plus wherever the player is), reading every one of them **before** mutating anything, since the removal pass has to judge each easyWp waypoint against the whole picture including the dimensions its shared twin projects into. The button calls `refreshItemWidgets()` afterwards because the screen only rereads the list when something tells it to — the change would otherwise stay invisible until the next keystroke or dimension switch.

**Import's dedup is `XaeroSync.existingIdentities`**: one `HashSet` of every waypoint's identity, built once per Import and grown as waypoints are added — it used to rescan the whole list per Xaero waypoint. It held the projected identities of shared waypoints too until 1.4.0, so a shared waypoint's exported Nether image was not imported back as a duplicate; that image is now a waypoint of its own (the split on load), whose plain identity does the same job.

`ModConfig.XaeroIntegration` holds just `enabled` (default `true`) and `xaeroChatFormat` (default **`false`**); `pushOnChange`, `autoImport` and `writeFiles` went with the machinery they configured — there is nothing periodic left to switch off, and the file fallback is no longer a choice but what happens when the live path can't run. `enabled` is a pure master switch: it decides whether the two buttons appear at all (alongside Xaero being installed) and whether either action does anything. It is a group added whole, for the field-initializer-vs-Gson-zero-value reason noted in Persistence above. Note the asymmetry that rule creates when a default is *changed* rather than added: `xaeroChatFormat` flipped from `true` to `false`, but a `config.json` that already carries the key keeps whatever it saved — only a fresh config, or one missing the whole group, picks up the new default.

**Both Xaero config rows are greyed out when Xaero isn't installed**, via `ModConfigScreen.gated(...)`, which clears `active` and attaches a `Tooltip` explaining why (`easywp.config.xaero_missing`). The section header stays visible so the integration is still discoverable; what it avoids is a live toggle that silently changes nothing, which reads as a bug rather than as an unmet requirement. Vanilla's own options widgets already grey their label out when inactive, so no custom drawing is involved.

The waypoint-list share button's chat message (and `/easywp share`'s, both through `WaypointShare.chatLine`) is `WaypointShareFormat`'s `NAME >>> DIMENSION X Y Z` line. With `xaeroIntegration.xaeroChatFormat` on (not the default) it goes through `XaeroWaypointFormat.chatShareLine` instead, producing the `xaero-waypoint:` line Xaero's own chat listener recognizes on a recipient's end and offers an `[Add]` button for. That one is opt-in rather than default precisely because a recipient *without* Xaero sees the raw tag string instead of a readable sentence, and most recipients are in that position. Clicking `[Add]` is handled entirely on Xaero's side and lands in Xaero's own list; reaching easyWp's list then takes an Import click, where it used to be picked up by the poll.

**The two buttons sit in the screen's bottom-right corner, mirroring the config gear in the bottom-left** — same 20x20 `ModernButton`, same 8px margin, and like the gear they are anchored to the **screen** rather than to the modal, so neither moves when the modal's contents do. Import is the inner one, Export the outermost (`xaeroButtonX(1)`/`xaeroButtonX(0)`). They are created in `init()`, not `refreshItemWidgets()`, since nothing about them depends on the list contents, and gated on a `showXaeroButtons` field resolved once per `init()` and read by both the widget creation and the glyph drawing so the two can never disagree about whether the buttons exist. Their glyphs (an arrow onto/off a bar — the universal download/upload pair, the bar being what distinguishes them from the bare scroll arrows) are hand-drawn with `fill` rather than added as texture assets, the same choice `drawSortIcon` already documents for the same reason: one size, one colour pair, no asset worth the round trip. Being icon-only they carry a real `setTooltip(Tooltip.create(...))` — `AbstractWidget.setTooltip` exists in all three versions and `AbstractWidget.extractRenderState` calls `refreshTooltipForNextRenderPass` itself, so `ModernButton`'s own override of the contents hook doesn't bypass it. Deliberately **not** duplicated into `ModConfigScreen`, where an earlier Import/Export action row lived: two places to click for the same thing, with nothing to tell the player which.

**The chat-share line is a genuinely different field layout from the file line, not the same one with a different tag - this was a real bug, not a hypothetical one.** An earlier version of `chatShareLine` built it by slicing `serialize`'s file-line output, on the assumption the two formats matched past the tag; they coincidentally have the same field *count* but diverge in meaning from field 7 onward, so the line parsed on Xaero's end without throwing but behaved wrong, and `[Add]` silently did nothing. Disassembling `WaypointSharingHandler` (both the outgoing `StringConcatFactory` recipe in `onShareConfirmationResult` and the validating parser in `onWaypointAdd(String[])`) turned up the real layout - `name:initials:x:y:z:color:rotation:yaw`, with an optional 9th "destination details" field - and, critically, that the 9th field is not just unused but actively harmful to include: `onWaypointAdd` only attempts to resolve a destination world when the split array has more than 9 elements, falling back to "the receiving player's current world" otherwise, which is exactly what a waypoint shared in chat should do. The earlier bug sent this mod's own Xaero waypoint-set name in that slot; since it was neither the literal `"External"` nor an `"Internal-<matching path>"` token Xaero recognizes, the receiving parser failed to resolve a destination, logged one line to Xaero's own client log, and added nothing - no exception, no chat error, nothing visible to either player, which is exactly why this took three rounds of "the Add button still doesn't work" to actually pin down instead of surfacing as an obvious crash.

### i18n

All translated text — UI strings and keybinding names alike — lives in the lang JSONs under `common/src/main/resources/assets/easywp/lang/`, so a new language is one new file and no code. `I18nHelper` used to hold the UI strings itself, in a hand-written `switch` duplicated across both version trees; it is now a one-method bridge that prefixes a short key with the `easywp.` namespace and returns `Component.translatable`. Keys stay short in Java (`menu.title`, `sort.name`) and namespaced in the files (`easywp.menu.title`) — unprefixed keys would collide with vanilla and other mods in the global translation registry. `WaypointSortMode` and `WaypointDisplayMode` return those same short keys from `getTranslationKey()`.

Three things about the lang files are not obvious and will silently break text if ignored:

- **Regional locale codes are resolved by exact match, no fallback chain.** `LanguageManager.onResourceManagerReload` builds a two-entry list — `en_us`, then whatever the client's exact selected code is (`es_mx`, `es_ar`, ...) — and hands it to `ClientLanguage.loadFrom`, which loads `lang/<code>.json` per namespace and silently skips it if that exact file is absent for that namespace (logged as "Skipped language file", not an error). There is no `es_mx` → `es` → `en_us` cascade: a player on any Spanish variant other than `es_es` falls all the way back to English for this mod's strings unless that exact file exists. Confirmed against Mojang's own asset index, Minecraft ships seven Spanish locale codes (`es_ar`, `es_cl`, `es_ec`, `es_es`, `es_mx`, `es_uy`, `es_ve`), so all seven ship here, all identical in content to `es_es.json` — reproducing what the old `I18nHelper.isSpanish()`'s `code.startsWith("es_")` used to do for free. A new Spanish-family locale Mojang adds later needs its own duplicate file for the same reason.

- **The format specifiers are not `String.format`'s.** Minecraft's translation formatter accepts only `%s` (and positional `%1$s`), plus `%%` for a literal percent. A `%d` or `%.1f` raises `TranslatableFormatException` — caught by vanilla, so the raw untranslated string is displayed — and a bare `%` raises an `IllegalArgumentException` that vanilla does **not** catch. Numbers needing a fixed number of decimals are therefore formatted by the caller and passed as strings; `ModConfigScreen.ConfigSlider` takes a `decimals` argument for exactly this, which is why its labels read `Size: %s%%` rather than the old `Size: %.0f%%`.
- **A `§` colour code stops applying at the next placeholder.** A translated string is split into one part per placeholder, and `TranslatableContents.visit` hands *every* part the component's own style, so formatting opened in one part does not carry into the next. Text that has to keep one colour across a placeholder sets that colour in Java instead — see the two `create.feedback_*` messages in `WaypointCreateScreen`, which apply `ChatFormatting.GRAY` to the whole component so the name and coordinates stay grey.

### Mixins

The mod injects no mixins at all. One mixin config exists and is registered: `easywp.mixins.json` (package `com.easywp.mixin`, common/server, empty), shared via `common/src/main/resources/` and requiring `JAVA_25` compatibility with `requireAnnotations: true` — kept as a wired-up extension point rather than deleted, so adding a common/server mixin needs no new plumbing. There is no client-side config: if client mixins are ever needed, `easywp.client.mixins.json` has to be written and added to every `fabric.mod.json`'s `mixins` array.
